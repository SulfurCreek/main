# 實作規格：用 LLM prompt 從 tCodeDutyNM 補齊正向推薦缺格

> 本文件是**實作分析與規格**，不含執行結果。交給實作模型照此執行。
> 來源檔：[`推薦模型訓練回饋.csv`](推薦模型訓練回饋.csv)（35,660 列）
> 產出檔：`推薦模型訓練回饋_補齊.xlsx`（**必須是 xlsx**——CSV 無法標示儲存格底色）

## 缺口盤點（已完成）

| 項目 | 數量 |
|---|---:|
| 需補齊的列（正向項數 < 5） | 34,770（97.5%） |
| 缺格總數 | 107,938 |
| 不重複職缺標題數 | **32,661** ← LLM 呼叫次數上限（見快取策略） |

正向項數分布：1項 13,242 列／2項 12,202／3項 9,038／4項 288／5項(已滿) 890。

## 核心規則（依業務端指示，不可違反）

1. **只補空格，不動既有資料**——已存在的正向推薦以原本的為準，一格都不能改。
2. LLM 候選**依 confidence_score 由高到低**依序填入空格，直到該列 top5 補滿。
3. **凡是 LLM 補的儲存格必須改底色**，與廠商原始資料視覺區隔。
4. LLM 回應中的 reason／格式說明全部捨棄，只取類別名稱填入。

## 實作步驟

### 步驟 0：準備 duty_data

從 [`../tcode/data_tCodeDutyNM.md`](../tcode/data_tCodeDutyNM.md) 取出全部葉節點
（614+ 葉，含 CodeNo 與名稱），組成 prompt 的 `{duty_data}`。
**用 MD 資料層，不要讀 Excel**（專案鐵則）。
建議格式每行一筆：`code<TAB>名稱`，全部塞進 prompt（614 筆約可控制在數千 token）。

### 步驟 1：以「職缺標題」為單位呼叫 LLM（快取去重）

- `{keyword}` ＝ 職缺標題原文（**不是** duty，是標題——要補的是「這個職缺還適合什麼職類」）。
- 同標題只呼叫一次，結果快取後套用到該標題的所有列（32,661 次呼叫，不是 34,770 次）。
- `{top_n}` 建議 **10**：候選會被過濾（見步驟 2），要留餘裕確保過濾後仍夠填滿缺格
  （最多缺 4 格；top_n=10 經過濾後不足的機率極低，不足時允許該列留白，不強補）。
- 使用者提供的 prompt 原文照用（見附錄），僅代入三個變數。
- **快取落地成中間檔**（如 `_llm_fill_cache.json`：標題 → 排序後候選清單），
  中斷可續跑、且可稽核 LLM 到底回了什麼。

### 步驟 2：候選過濾（填入前逐項檢查，順序執行）

對每列，把該標題的 LLM 候選依分數高→低逐一檢查，通過才填：

| # | 過濾規則 | 理由 |
|---|---|---|
| 1 | `category_name` 必須存在於 tCodeDutyNM 葉清單（名稱與 code 都要對得上） | 防 LLM 幻覺類別 |
| 2 | 不得與該列**既有正向推薦**重複 | 不可動原資料、不可重複 |
| 3 | 不得出現在該列**負向推薦1~5** | 負向是要壓下去的，補進正向會自相矛盾 |
| 4 | 不得與該列**已由 LLM 補入的項目**重複 | 同列去重 |

通過的依序填入 `正向推薦_k` 的空格，直到滿5格或候選用盡。
（現行模型第6~10名的項目**允許**被 LLM 選中——那些不是負向，且順序調整情境本來就有正解在那。）

### 步驟 3：寫出 xlsx 並標底色

- 用 openpyxl 從 CSV 資料建新活頁簿（欄位、列順序與 CSV 完全一致）。
- **LLM 補入的儲存格**套 `PatternFill`，建議 `FFF2CC`（淡黃）——只標補入格，
  廠商原始正向格、負向格、其他欄位一律不動樣式。
- 第1列放欄位標題（xlsx 不需要 CSV 的 `#` 註解列，改在 README／工作表名註記）。
- 原 CSV **保留不動**，作為「未補齊前」的對照基準。

### 步驟 4：驗收（實作完必跑）

| # | 檢查 | 通過條件 |
|---|---|---|
| 1 | 原資料完整性：逐格比對 xlsx 與原 CSV 的非空欄位 | 100% 一致（一格都沒被改） |
| 2 | 補入格 ＝ 上色格 | 兩個集合完全相等（不能有補了沒上色、或上色了沒補） |
| 3 | 補入項全部存在於 tCodeDutyNM 葉清單 | 0 筆幻覺 |
| 4 | 補入項與同列負向推薦交集 | 0 |
| 5 | 補入項與同列既有正向重複 | 0 |
| 6 | 補齊後仍未滿5格的列數 | 回報數字（允許存在，不強補） |
| 7 | 抽查 10 列人工核對語意合理性 | 附在完工報告 |

## 決策點（實作前需業務端確認，或採建議值）

1. **信心分數下限**：使用者指示「依分數排序補到滿」，未設門檻。
   建議仍設**下限 60**——低於此寧可留白（本資料集鐵則：留白比猜錯安全；
   歷史上曾因亂補值污染訓練資料，見
   [`../feedback_訓練標籤污染撤回說明.md`](../feedback_訓練標籤污染撤回說明.md)）。
   若業務端要求無條件補滿，把門檻設 0 即可，邏輯不變。
2. **LLM 供應商/模型**與並發速率：32,661 次呼叫，需估算成本與時間，由實作端定。

## ⚠️ 與本資料集紅線的關係（重要澄清）

本資料集紅線寫「不准拿模型輸出當正解補值」——該紅線防的是**拿被修正對象（推薦模型自己）
的錯誤輸出**回填。本次補齊是業務端明確指示、用**獨立的 LLM ＋ tCodeDutyNM 全清單**重新判斷，
且每一格都以底色標示、可稽核可撤回，性質不同。但仍要求：
- 補入格永遠可透過底色一鍵識別/移除（可逆性）；
- 快取檔保留 LLM 原始回應（含分數）供追溯；
- 絕不覆蓋任何廠商原始資料。

## 附錄：Prompt 原文（照用，代入 {duty_data}／{keyword}／{top_n}）

```
你是一個職務類別推薦系統。根據使用者提供的關鍵字，從以下職務類別清單中推薦最相關的類別。

# 所有職務類別
{duty_data}

# 使用者輸入的關鍵字
{keyword}

# 任務要求
1. 根據關鍵字的語義，推薦最相關的 {top_n} 個職務類別
2. 為每個推薦提供信心分數（0-100），表示該類別與關鍵字的相關程度
3. 簡要說明推薦理由（1-2 句話），解釋為什麼這個類別適合該關鍵字

# 輸出格式要求
請嚴格按照以下 JSON 格式回應，不要包含任何其他文字說明：

[
  {
    "category_code": 1234,
    "category_name": "類別名稱",
    "confidence_score": 85,
    "reason": "推薦理由說明"
  },
  {
    "category_code": 5678,
    "category_name": "另一個類別",
    "confidence_score": 72,
    "reason": "另一個推薦理由"
  }
]

注意事項：

* 必須返回純 JSON 陣列，不要用 markdown 代碼塊包裹
* confidence_score 必須是 0-100 的整數
* 推薦結果按信心分數從高到低排序
* 確保推薦的類別代碼和名稱確實存在於上述職務類別清單中
```

實作端注意：即使 prompt 要求純 JSON，仍要防禦性解析（strip markdown 圍欄、
驗證 JSON schema、code/名稱對不上 tCodeDutyNM 就整筆丟棄該候選）。
