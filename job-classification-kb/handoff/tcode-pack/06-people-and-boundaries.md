# 06 — 角色與邊界

> 角色定義逐字抄自 `job-classification-kb/tcode/04-change-workflow-sop.md`〈角色與職責〉；邊界（本 KB 可以做什麼／不能做什麼）為本次打包時依對話中出現過的使用者裁決與 CLAUDE.md 治理規則整理。

## 角色與職責

| 角色 | 負責什麼 |
|---|---|
| **需求端** | 流程的起點，提出「要新增/修改哪個代碼」的原始需求，交給企劃。 |
| **企劃** | 全程主導：確認改哪張表／哪個層級、開工單給 Perry、催各專案同步、發求職公告。是這個流程的驅動者。 |
| **Agent（Claude／Antigravity）** | 執行填表的機械性工作：把異動代碼填進表格、填 `ChangeType`、派發代碼、補語系翻譯、產出修改需求文字給企劃開工單用。企劃判斷完「改什麼」之後交給 Agent 代勞，不用自己手動一格一格填。 |
| **Perry** | 持有/保管「最新留存總表」的人；收到工單後安排正式更新排程，通知主要專案套用。 |
| **主要專案** | 實際把異動寫進正式代碼表的工程單位（即本 KB 一路追蹤的「工程師」）。 |
| **其他使用該代碼的專案** | 不是主要擁有者，但有引用這張代碼表，異動後需要自行同步（企劃負責提醒，不負責幫他們改）。其中 **DBA** 要記得把新代碼表傳給**資科侑丞**，讓他更新職類推薦模型——這一步最容易被忘記，公告發了但模型沒更新，推薦結果會跟新代碼對不上。 |
| **維運** | 求才端公告發布窗口。 |
| **企劃（求職公告）** | 求職端公告另外由企劃自己發，跟維運的求才公告是平行的兩條，不是同一份。 |
| **黃總** | 最終把關者，公告發出、各系統都上線後，由黃總確認配對（求才/求職媒合）已經依新代碼正確運作。 |

## 本 KB／Agent 可以做的事

- 比對「修改前檔案」vs「修改後檔案」兩份獨立檔案，找出真正的異動（不依賴 ChangeType 單一欄位）。
- 核對企劃填好的異動表是否正確、完整（消失代碼是否都有 `Old_CodeNo`、新增欄位有沒有缺漏、ChangeType 是否殘留舊標記）。
- 把異動代碼填入表格、填 `ChangeType`、派發代碼、補語系翻譯（這幾項是 SOP 裡明確劃給「Agent」的機械性工作）。
- 產出要開工單用的異動清單／公告文字草稿，給企劃直接拿去填工單或發公告。
- 維護 KB 自己的資料層副本（`TCode_Export.xlsx`、`data_*.md`），但要在副本落後於官方流程時誠實標註，不要讓舊副本冒充現況（見 `02-iron-rules.md` 第 7 條）。
- 自我複檢（AI 複檢）：SOP 明確要求 Agent 產出修改需求後要先自己重新核對一次有沒有錯漏、漏掉的一對多合併項目等。

## 必須由使用者核可或交給別人的事

- **人工檢查（human in the loop）放行**：Agent 的「產出修改需求」不能直接變成工單，必須經過企劃本人過目確認無誤才能往下走（SOP 明文的第二道關卡）。
- **開工單給 Perry**：由企劃執行，不是 Agent 的工作範圍。
- **安排正式更新排程、通知主要專案**：Perry 的職責。
- **發布對外公告**（求才公告由維運發、求職公告由企劃發）：不是 Agent 可以直接對外發布的內容，Agent 只能產出草稿文字。
- **確認配對（媒合）結果已更新**：由黃總把關，是整個流程的終點，不在 Agent 或 KB 的權限範圍內。
- **對「原本規劃合併 vs 改成只新增」這類會影響既有代碼去留的裁決**：必須由使用者明確裁示（例如 WorkAbility 310000 大類最終改成不合併，就是使用者直接拍板，不是 KB 自行判斷）。
- **共用資產（`.claude/skills/`、`wiki/`、`CLAUDE.md`、`scripts/`、`.claude_index.md`、`.claude/settings.json`）的修改**：依 repo 治理規則，只能由主幹管理 session（Repo Steward）修改，本 KB 分支／Handoff 助手都不可以直接改，需要時在 PR 描述註明「請主幹對照吸收」。
