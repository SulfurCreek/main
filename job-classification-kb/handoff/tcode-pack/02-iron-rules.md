# 02 — 技術側鐵則（怎麼看代碼表、怎麼處理異動）

> 來源：`job-classification-kb/tcode/04-change-workflow-sop.md`〈技術側的鐵則〉＋`.claude/skills/tcode-excel-ops/references/bulletinboard-rules.md`〈資料來源鐵則〉＋本 KB 踩過的坑整理而成的「方法論」。本檔**只談怎麼判斷、怎麼核對，不帶任何具體代碼表版本、筆數或 CodeNo**——那些屬於某一輪異動的具體內容，不是通用方法。

## 1. 判斷真的改了什麼，要比對「修改前」vs「修改後」兩份獨立檔案，不要只信 ChangeType

- **規則**：要確認一張 tCode 表真的改了什麼，必須拿到「修改前檔案」與「修改後檔案」兩份獨立檔案，逐列比對代表名稱的欄位（小類/中類/大類名稱），不能只信表格自己填的 `ChangeType` 欄位。
- **為什麼**：`ChangeType` 常常掛著沒清（可能是為了別的原因動過那一列，但內容其實沒變），也可能比對時誤用了錯的 baseline 版本，生出假異動。單一文件的自述（它自己標的異動類型）不可信，要用「外部對照」驗證。
- **方法**：拿到兩個版本 → 先用 CodeNo 當 key 做 join（注意第 4 點的型別問題）→ 逐欄比對名稱/分類是否真的不同 → 只有「比對出真的不同」才算異動，光是 ChangeType 欄位有標記不算數。
- **完整方法論**：`.claude/skills/tcode-excel-ops/references/bulletinboard-rules.md`〈資料來源鐵則〉（已完整複製於本包 `05-skills-bundle/tcode-excel-ops/references/bulletinboard-rules.md`）。

## 2. 合併類異動（move／move_edit）：被合併的每個舊代碼都要各自一筆紀錄

- **規則**：一對多合併時，每一個被合併掉的舊代碼都要在異動清單裡各自佔一筆 `move`，不是一個新代碼配一筆；核對時要逐筆核對每個舊代碼的「去向」，不能只看最後剩下的新代碼存不存在。
- **為什麼**：容易漏記成「只留最後一筆代表整批合併」，實際上每個舊代碼都該有獨立的異動紀錄，不然事後查不出某個特定舊代碼到底去了哪裡。
- **方法**：看到多個舊代碼指向同一個新代碼時，先確認異動清單裡是不是真的有對應數量的列，而不是只有一列代表「這群代碼合併了」。

## 3. 驗證「消失的代碼」是否正常：看有沒有被 designated 到新代碼，不是看它還在不在

- **規則**：代碼消失本身不是問題，只要能在某一筆紀錄的「舊代碼參照欄」查到，就算正常異動；查不到才是真的漏記。
- **為什麼**：單純看「這個代碼現在還存不存在」會誤判——一對多合併時，只保留最後一筆的情況是正常的，不代表其他舊代碼沒被處理。
- **本 KB 自己踩過的坑**：核對「舊代碼是否都有對應新代碼」時，曾用「舊代碼當 key 建字典」的寫法（`{code: row for row in rows}`）來快速查詢。**這個寫法有嚴重風險**：如果多筆紀錄共用同一個目標（例如好幾個舊代碼都合併進同一個新代碼），用字典的方式建索引會讓後面的紀錄蓋掉前面的，看起來「只剩最後一筆」，造成誤報「前面幾筆沒有被處理」。
  - **教訓**：核對「每一筆舊代碼是否都有對應」時，要逐筆檢查原始清單，不要用「代碼當 key 去重」的方式做索引，去重動作本身就會把合法的重複情況洗掉。

## 4. 代碼欄位型別要先正規化再比對

- **規則**：代碼欄位（CodeNo）從不同來源（Excel／CSV／不同工具匯出）讀出來，型別可能不一致（例如一邊是整數字串、一邊是帶小數點的浮點數）。比對前要先統一轉成同一型別（例如都轉成字串）再做比對。
- **為什麼**：型別不一致會導致理論上相同的代碼互相比對不上，誤判成「查無此代碼」，進而產生一堆假的異動或假的遺漏。
- **方法**：任何跨檔案、跨欄位的 CodeNo 比對之前，先確認兩邊的型別一致，有疑慮就先統一轉型。

## 5. 大類／中類改名要 cascade 到底下所有子節點

- **規則**：大類或中類改名時，底下所有子節點（小類／葉）顯示用的大類/中類名稱欄位也要跟著更新，不能只改那一列的標題。
- **為什麼**：如果只改標題列、不往下更新，會出現「中類名稱已經是新的，底下葉節點卻還寫舊名稱」的父子不一致，查詢或顯示時會出現矛盾資訊。
- **方法**：改完大類/中類名稱後，要額外做一次「往下掃描子節點、確認名稱欄位是否同步」的檢查，不能假設改了標題列就等於全部改完。

## 6. 裁決從「合併」改成「只新增」時，要確認兩邊都改乾淨

- **規則**：如果原本規劃是合併（舊代碼併入新代碼），後來裁決改成「只新增、兩邊並存」，要同時確認：(a) 原本規劃被合併的舊代碼有沒有真的恢復成「未變動」狀態；(b) 新代碼的異動類型／舊代碼參照欄位有沒有清掉合併痕跡（例如從「合併」改回「新增」、參照欄清空）。
- **為什麼**：裁決改變時很容易只改一邊——例如只把舊代碼恢復了，卻忘記把新代碼身上殘留的「合併」標記清掉，或者反過來。兩邊沒有同步改，表格會處於不一致狀態。
- **方法**：裁決變更後，要同時檢查「被牽涉到的每一個代碼」（不管是舊代碼還是新代碼）的異動類型與參照欄位，確認跟最新裁決一致，不要只改其中一邊就收工。

## 7. 核對資料層副本（MD 摘要／data 檔）之前，先確認它有沒有過期

- **規則**：本 KB 維護的 `data_*.md` 資料層副本，更新時機通常落後於「已經確認套用」的異動——因為副本是等官方匯出檔到貨後才重建，不是異動一提出就同步。使用這些 MD 檔案回答「現在長怎樣」之前，要先確認它是不是已經涵蓋了最近一輪的異動。
- **為什麼**：如果直接信任 MD 檔案的數字（筆數、葉數等）當作「現況」，可能會漏看最近才確認套用、但 MD 還沒重新產生的異動，得出過期的結論。
- **方法**：核對任何「現況」問題之前，先問自己：這份 MD 是哪一次官方匯出重建的？最近有沒有確認套用過、但這份 MD 建立之後才發生的異動？有疑慮就直接去源頭（官方匯出檔）核對，不要只信 MD 摘要。
