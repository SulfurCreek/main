### F4.2 審查者的質疑

- [HR]「透過實測、工程確認及維運與稽核訪談」→ 我們的 PM 要直接跟客戶訪談，這裡訪的都是內部單位，客戶端看不太到。 → 面試追問 → 要打消疑問需看到：直接訪談企業客戶的對象類型、次數，以及訪談後改了哪項規格。
- [HR]「協助製作銷售簡報」→ 有支援業務，但不確定他有沒有上過客戶會議、做過展示。 → 面試追問 → 要打消疑問需看到：陪同業務見客或產品展示的一個實例。
- [主管]「與外部合作夥伴及工程議定查詢規格，涵蓋簽章驗證」→ 這對我們跨系統整合很對味，但只在技能欄，不知道是哪個案子。 → 仍然約談 → 要打消疑問需看到：串接對象、資料交換流程與本人負責的規格段落。
- [主管]「先做第二名、已有規劃基礎的搜尋結果頁」→ 會講清楚為何延後第一名，取捨思路不錯；但兩項都還在開發或封測。 → 仍然約談 → 要打消疑問需看到：上線後用來判斷取捨是否正確的指標。
- [主管]「男性 DAU 在 6 週內由約 3,200 增至 1.25 萬」→ 數字漂亮，但同時寫了配合行銷導流，成長多少是他的？ → 面試追問 → 要打消疑問需看到：本人負責的範圍與導流量的拆分。

### F4.3 評語

**結論**：interview／Level 7——「負責人力銀行企業端招募系統」加 API 規格與 Scrum 證據，對應必要條件；客戶訪談與售前待驗證。

**做得好**
1. 1111 經歷第 1 條｜「採新舊並行、分階段上線」｜展現企業級系統迭代與交付規劃，對應職責 3、5、6。
2. 技能欄 API 協作｜「簽章驗證、時間戳與防重放、錯誤碼、頻率限制」｜直接對應必要條件「API 串接」與職責 4。
3. 1111 經歷第 4 條｜「考量得票第一的切換帳號功能複雜度高」｜有依據的 Roadmap 取捨，對應產品策略職責。

**可改進**
1. 1111 經歷第 1 條｜「透過實測、工程確認及維運與稽核訪談」｜requirement｜interview_follow_up｜JD 首要職責是直接客戶訪談，面試會先問｜若有，補一例直接訪談企業客戶的對象與改變的規格。
2. 1111 經歷第 3 條｜「協助製作銷售簡報」｜requirement｜interview_follow_up｜售前支援只見內部說明｜若曾參與客戶會議或展示，補一句情境。
3. 1111 經歷第 1 條｜「2025/10 完成登入、首頁等功能上線」｜measurement｜interview_follow_up｜代表作只有交付｜補可得的使用或客服觀察，附期間與基準；沒有就維持現狀。
4. 技能欄 API 協作｜「與外部合作夥伴及工程議定查詢規格」｜readability｜editorial｜整合能力藏在技能欄，主管不易連到案例｜在經歷中加一句對應專案與用途。
