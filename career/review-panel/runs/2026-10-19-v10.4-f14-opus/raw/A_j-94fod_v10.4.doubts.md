### F4.2 審查者的質疑

- [HR]「系統服務逾 6 萬家活躍付費廠商（2026 Q3）」→ 規模是系統的，不是他做出來的；不過能看出環境複雜度 → 仍然約談 → 要打消疑問需看到：他負責的模組實際觸及多少廠商、哪些上線後有使用數據
- [主管]「與外部合作夥伴及工程議定查詢 API 的簽章驗證、時間戳、錯誤碼」→ 這段很像我們要的 TPM，技術語彙到位；但議定跟驗收是兩回事 → 面試追問 → 要打消疑問需看到：一份去識別的 API 規格或他寫的驗收案例
- [主管]「與工程分階段交付，登入、首頁等功能於 2025/10 上線」→ 交付有，但我們要的是里程碑、範圍變更、客戶期待管理，這裡看不到他怎麼控時程與風險 → 面試追問 → 要打消疑問需看到：一次延期或範圍調整的實際處理過程
- [主管]「網頁付款占營收由 24% 升至 80% 以上」→ 支付很對口，但占比翻倍可能主要是商店抽成政策驅動，本人貢獻多少？ → 面試追問 → 要打消疑問需看到：本人推動的具體動作（導流設計、價差）與其他影響因素
- [HR]「先推進第二名的搜尋結果頁，延後第一名的切換帳號功能」→ 少見有人寫出被延後的項目與理由，判斷依據清楚，但兩案仍在開發 → 仍然約談 → 要打消疑問需看到：上線後的結果或取捨是否被驗證

### F4.3 評語

**結論**：interview／Level 7——「議定查詢 API 的簽章驗證…頻率限制」等必要條件有證，TPM 時程風險與上線成效待面試確認。

**做得好**
1. 1111 經歷第 6 點｜「議定查詢 API 的簽章驗證、時間戳、錯誤碼、頻率限制」｜直接對應「理解 API、系統串接」必要條件
2. 1111 經歷第 4 點｜「先推進第二名的搜尋結果頁，延後第一名的切換帳號功能」｜顯示優先順序判斷與依據
3. 尚凡第 3 點｜「以售價不變的 Android 作對照…團隊依結果決定採用低價」｜有對照、期間、決策，對應成效追蹤與支付

**可改進**
1. 1111 經歷第 1 點｜「登入、首頁等功能於 2025/10 上線」｜measurement｜interview_follow_up｜JD 重成效追蹤，現只見交付｜補一項上線後追蹤的指標或問題處理事實
2. 1111 開頭段｜「採新舊並行、分階段上線」｜requirement｜interview_follow_up｜TPM 的範圍/里程碑/變更管理看不到｜補一次時程或範圍變更如何處理
3. 尚凡第 4 點｜「網頁付款占營收由 24% 升至 80% 以上」｜ownership｜interview_follow_up｜歸因會被追問｜補本人推動的動作與外部因素
4. 專業摘要｜「涵蓋訂閱制社交 App、網紅媒合平台與人力銀行招募系統」｜readability｜editorial｜支付串接經驗埋在後段｜投此職可在摘要點出金流與第三方串接經驗
