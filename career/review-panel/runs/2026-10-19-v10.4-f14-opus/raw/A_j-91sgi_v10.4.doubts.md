## F4.2 審查者的質疑

- [HR]「導入 CodaPay，讓印尼、泰國等市場的用戶可用電信帳單與超商付款」→ 有金流經驗，但是 2016–2018 的事，最近四年都在做招募系統，跟我們支付場景有段距離。 → 仍然約談 → 要打消疑問需看到：近期是否有任何計費、付款或對帳相關工作的具體範圍。
- [主管]「2020/11–2021/09，網頁付款占營收由 24% 升至 80% 以上」→ 數字很漂亮，但這段期間蘋果政策與價差都會推動，看不出他本人設計了什麼讓用戶改走網頁。 → 面試追問 → 要打消疑問需看到：本人定義的導流機制（入口、價差、提示）與同期外部因素說明。
- [主管]「議定查詢 API 的簽章驗證、時間戳、錯誤碼、頻率限制與 JSON 欄位規則」→ 正面但保留：懂 API 安全面，對支付串接是好訊號；但不確定是他定規格還是工程定、他只是確認。 → 面試追問 → 要打消疑問需看到：他寫的 API 規格文件或驗收案例片段。
- [主管]「依結果決定採用低價」→ 對照組實驗設計得像樣，但還原原價後跌 65% 這麼大，我會想知道有沒有考慮季節或促銷干擾。 → 面試追問 → 要打消疑問需看到：當時排除干擾的方法或資料限制說明。
- [HR]「與 CodaPay 新加坡技術團隊協調串接」→ 有對外夥伴對接，但 JD 加分項是銀行、政府機關，履歷完全沒提。 → 面試追問 → 要打消疑問需看到：是否有與銀行、電信或主管機關對接的實例。

## F4.3 評語

**結論**：interview／Level 8——必要條件皆有證據，「Peach 網頁付款占營收由 24% 升至 80% 以上」直接對應金流規劃。

**做得好**
1. 尚凡｜「規劃 Peach 付款由 App 內購轉向網頁…24% 升至 80% 以上」｜付款管道轉換有期間與比較，對應支付產品規劃。
2. 1111｜「議定查詢 API 的簽章驗證、時間戳、錯誤碼、頻率限制」｜直接回應「理解 API 串接」必要條件，且涉及安全風險。
3. 思維特｜「整理各管道的抽成、稅、手續費與撥款週期，完成實收試算」｜金流成本思維，對支付平台商業判斷有用。

**可改進**
1. 尚凡 Peach｜「規劃 Peach 付款由 App 內購轉向網頁」｜ownership／measurement｜interview_follow_up｜面試會被追問歸因｜補本人設計的導流或付款流程規則一句，不改數字。
2. 專業摘要｜「推進 App 內購轉向網頁付款」｜readability｜editorial｜支付職缺審查者需翻到第二段才看到金流證據｜投此類職缺時把 CodaPay 多管道付款與實收試算前置。
3. 1111 經歷｜「系統服務逾 6 萬家活躍付費廠商」｜requirement｜interview_follow_up｜支付經驗看起來停在 2021｜若曾參與計費、方案購買或對帳，補一句本人範圍。
4. 全文｜（未呈現）銀行／政府對接｜requirement｜interview_follow_up｜加分項無證據，不阻擋面試｜若有銀行、電信或主管機關對接實例，補對象與動作；沒有就不寫。
