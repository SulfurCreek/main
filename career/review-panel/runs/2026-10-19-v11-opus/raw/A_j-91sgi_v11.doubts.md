## F4.2 審查者的質疑

- [HR]「推進智冠金流串接」→ 有金流經驗，對支付職缺是加分，但「推進」到底是寫規格還是只追進度？ → 面試追問 → 要打消疑問需看到：串接時本人產出的規格或驗收清單範例。
- [主管]「涵蓋簽章驗證、時間戳與防重放、錯誤碼、頻率限制」→ 這是我們要的，但放在技能欄沒掛案例，像清單。 → 面試追問 → 要打消疑問需看到：哪個專案、跟誰議定、本人定義了哪幾項。
- [主管]「網頁付款占營收由 24% 升至 80% 以上」→ 付款管道轉移很貼近我們，數字也有期間，正面；但不知是產品引導還是政策強推。 → 仍然約談 → 要打消疑問需看到：推動手段與轉換過程中掉單或客訴的處理。
- [主管]「還原原價後，iOS 非續訂營收較原價期減 65%」→ 還原後大跌比降價期變化還大，結論「採用低價」的推論我看不太懂。 → 面試追問 → 要打消疑問需看到：對大跌的解讀、樣本量與外部因素說明。
- [HR]「現任 1111 企業端招募系統 Product Owner」→ 近四年都在招募系統，轉回支付的動機沒寫。 → 面試追問 → 要打消疑問需看到：投遞動機中對支付/金流方向的說明。

## F4.3 評語

**結論**：interview｜Level 7——有金流實績（「推進智冠金流串接」），必要條件均無反證，銀行/政府對接待問。

**做得好**
1. 尚凡 Peach 條｜「網頁付款占營收由 24% 升至 80% 以上」｜付款管道轉移直接對應支付產品規劃。
2. 思維特 CodaPay 條｜「整理各管道的抽成、稅、手續費與撥款週期，完成實收試算」｜顯示對金流成本結構的理解。
3. 1111 第一條｜「與工程採新舊並行、分階段上線」｜既有資料與客戶限制下的交付能力，適用支付平台迭代。

**可改進**
1. 專業技能 API 協作｜「與外部合作夥伴及工程議定查詢規格」｜requirement｜interview_follow_up｜必要條件「理解 API 串接」只靠技能欄支撐｜在經歷條目補是哪個專案、本人定義的項目。
2. 尚凡定價實驗｜「還原原價後，iOS 非續訂營收較原價期減 65%」｜measurement｜interview_follow_up｜結論推論鏈不清｜補一句對大跌的解讀或已知限制。
3. 尚凡 Peach 條｜「規劃 Peach App 由內購轉向網頁付款」｜readability｜editorial｜Peach 首次出現無脈絡｜補產品類型。
4. 自傳末段｜「希望結合訂閱、定價與企業流程的經驗」｜requirement｜editorial｜投支付職缺時方向連結弱｜如屬實，補對金流/支付的意向。
