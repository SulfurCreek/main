# 104coverletter：104 自我推薦信（逐職缺客製）

> 維護：Career Move。依據：`career/104/cover-letter-research.md`（本人 2026-10-20 提供）。
> 與 `resume-craft/references/cover-letters.md` 的分工：那份是 A4 一頁的完整書信（Email／官網上傳）；**本 skill 只管 104 等平台「應徵時填的推薦信欄位」**。

## 1. 輸入

| 項目 | 來源 |
| :-- | :-- |
| 職缺 | 本人給的職缺代碼或名稱 → `career/review-panel/jd/routing.tsv` 找 code、公司、職稱；JD 原文：`career/targets/jobs.md`（必要時 `review-panel/jd/full/<code>.md`、`career/review-panel/jd/light-cards.md`） |
| 該職缺的驗證結果 | `review-panel/runs/` 最新一輪對該 code 的 `apply_hook`、`top_gap`、F 層 doubts（可用來選要打的亮點與要避開的缺口） |
| 事實 | `career/library/`（先 `INDEX.md`、`decisions.md`、`superseded.md`、`about-me.md`）；現行履歷 `drafts/<版本>/resume-<版本>.md` |
| 分級 | 本人指定「主力」或「一般」；沒說就當一般 |
| 主力職缺的產品觀察 | **只能由本人提供**（試用心得、觀察）；沒提供就用一般鉤子，不自己研究編造 |

## 2. 結構（250–350 字；欄位上限 2,000）

> 依據：企業端詳細頁**全文展開、純文字、一行約 45–50 字**，位置在履歷本文前、104「符合分析」上方（本人 2026-10-20 截圖）；104 官方建議「簡短精要，約 400–500 字尤佳」。詳見 `104/cover-letter-research.md`。
> - **純文字**：不用 HTML、粗體、Markdown；條列用「‧」開頭＋換行，最多 3 點，每點 1–2 行。
> - 段落之間空一行；不放網址（作品集網址若要放，放最後一行）。
> - 第一句就講職缺名與最相關實績（列表／通知信可能只露開頭，未證實但成本低）。
> - 若 104「符合分析」可能判「不太符合」的項目（年資、產業、學歷）與此職缺相關，可用一句說明落差，不辯解、不誇大。

```text
您好：
應徵【職缺名稱（與 JD 一字不差）】。〔破題：近 10 年產品經理經驗＋與此職缺最相關的一項實績；開頭兩句內要看得到職缺名與核心籌碼〕

‧〔直接寫做過的事：場景＋行動＋結果；不加「能力小標：」開頭〕
‧〔同上〕
‧〔可選第 3 點〕

〔可選一句鉤子：一般＝產業／商業模式共鳴；主力＝本人提供的產品觀察〕完整經歷在履歷中，謝謝您的閱讀。

聶崑淮
```

### 2.1 中英混合版（JD 英文優先或要求英文撰寫／溝通時）

- 結構：中文稱謂＋破題（約 100 字，可用「以下是三項相關經驗：」帶出）→ **英文條列 3 點（120–150 words）** → 中文結尾＋署名。**不解釋為何用英文**，也不寫「我英文很好」。
- 英文寫法依 **`career/style/voice-en.md`**（語域、責任範圍動詞對照、固定譯法、禁用詞）。
- 英文條列同樣只用 library 事實；動詞具體，不用 strategic、passionate、detail-oriented 這類形容詞；不寫 Jira、未有的效率百分比、adoption。
- 同檔保留全中文備選版，由本人選用。

## 2.9 強制門檻

**推薦信驗收工具（2026-10-27 起必跑）**：草稿交 Codex 前、定稿登錄前，各跑一次 `python3 career/scripts/verify_letter.py <檔案> --job "<職缺名>"`，0 違規才可交出。檢查：產品名首次提及必定義（JustDating、Juicy、Peach、KOOL、SweetRing、CodaPay；新產品名請補進 `ENTITY_DEFS`）、禁用詞與過度自信結尾、職缺名逐字。

先過 `career/skills/resume-causal-logic-compiler/SKILL.md` §1 編譯規則與 §2.3 披露檢查（推薦信只挑 2–3 點）。

## 3.0 七大鐵律：Stun the HR＋陌生人 3 秒秒懂（本人 2026-10-29，優先於下方舊條文；verify_letter.py 自動攔截）

推薦信只有 300～350 字，目標是 5 秒內讓人資想點開履歷，不是背產品名清單。

1. **去陌生產品代號**：Peach、JustDating、Juicy、KOOL、SweetRing 等內部產品名，草稿預設**不寫專名、不鎖入 LOCK_ENTITIES**，改用白話產品型態（「訂閱制內容 App」「主力高營收交友 App」「網紅雙邊媒合平台」「跨國交友 App」「東南亞第三方支付商」）。例外：對外極知名的品牌（1111 人力銀行、Airbnb、Instagram）；投支付／FinTech 職缺時 CodaPay 有直接加分可保留。**若寫了專名，該句必須同時交代它是什麼**（verify_letter 硬性攔截；未交代＝錯誤，寫了專名＝警告）。
2. **Stun Opening**：每點第一句結合「獨立場景主詞」與「高反差戰果或硬核限制」，再接核心方法。例：「在有限開發資源下，同時負責現有系統日常修改與整套系統重新改版，累計約 70 項主要功能上線」「為訂閱制內容 App 串接台灣金流商，將用戶從手機內購引導至網頁付款，網頁付款營收占比由 24% 升至 80% 以上」。
3. **獨立場景錨點**：推薦信沒有履歷的公司標題保護，每點開頭自帶場景主詞（「接手無文件留存的舊系統翻新…」「於經營跨國交友 App 期間…」）。不得以「截至 20…」或「帳號權限…」裸奔開頭（硬性攔截）。
4. **淘汰分母清單與履歷黑話**：不寫「帳號、登入、公司資料與聯絡人相關」這類報表分類（硬性攔截）；不寫「在工程資源有限下」（硬性攔截）；「兩線共用開發資源」改寫「在有限開發資源下，同時負責現有系統日常修改與整套系統重新改版」；「由內購轉向網頁付款」改寫「將用戶從手機內購引導至網頁付款」。
5. **一點一主線**：列點不加「能力標籤：」冒號小標（硬性攔截）；單一列點只講一條主線，不用 Separately／另外／此外 或分號硬湊兩件無關的事。
6. **事實邊界**：不寫 Singapore／新加坡／Russian／俄羅斯等未授權城市與國籍（硬性攔截）。
7. **結尾謙遜自信**：點出雙方產品或業務的共同點，以「期待能與團隊進一步交流，分享…的實務經驗」或「期待能將…運用在…」收束（結尾段必須含「期待」，硬性攔截）；不寫「可以直接投入」「直接解決」「立即解決」「可用於貴司」。

8. **稱謂與結尾 Hook（本人 2026-10-29）**：一律用「貴公司」，不寫「貴司／我司／敝司」（易被視為中國用語或公文稱謂；硬性攔截）。結尾不要替對方業務貼標籤或寫「與我目前的工作方向相近／經驗相關」這類天外飛來一筆（硬性攔截）；改為總結前三點的「核心產品課題共鳴」，再帶出期待與貴公司團隊交流。例：「貴公司的訊息整合與 AI 自動化課題，正是我過去幾年持續處理的問題。期待能與團隊進一步交流，分享…的實務經驗。」
9. **英文句法鐵律（同步 `style/voice-en.md` §6）**：痛點破題，不把核心痛點丟在句尾 `, which leave…` 子句；客戶需求用 `To address / In response to N client requests`，不用 `Backed by`（Backed by、`, which leave` 為硬性攔截）。

**新草稿流程**：寫完先跑 `verify_letter.py <檔> --job "<職缺名>"`；已送出的信在 `applications/INDEX.md` 標「已投遞」，`--all` 會略過，不回頭改。被新鐵律淘汰的舊定稿移到 `letters/archive/`。

## 3. 其他寫法規則（與 §3.0 衝突時以 §3.0 為準）

1. **事實只取 library**；數字沿用履歷口徑與限定詞（例：「上線與導流期間」「依公司公開資料」）。沒有的不補、不估。
2. **不照抄 JD 原文、不照抄履歷句子**：用同一事實換角度寫判斷或做法。
3. **缺口不硬補**：JD 要的 Jira、SQL、讀後端程式碼、近母語英文等，推薦信不提、不暗示具備；可改寫相近的真實能力（例：與工程確認後端行為）。
4. **不寫自我介紹開場**（「我是聶崑淮」）；名字只在署名，**署名只寫「聶崑淮」，不預設「敬上」**。
4a. **語氣直接、自然**：條列不加能力小標（如「生成式內容：」）、不解釋寫作安排、不做過度正式的書信包裝（本人 2026-10-21）。
5. 禁用：Spearheaded／主導開發、第一大、案主／業主、AI 套話（「深感契合」「願景高度契合」「在瀏覽貴公司職缺後」）、乞求句（「懇請給予機會」）、軟性形容詞（積極進取、抗壓性強）。
5. 不放電話、Email、地址（履歷已有）。對外不寫 1111 內部系統名、代碼表名。
5a. **結尾要謙和（本人 2026-10-27）**：pursuing voice 只用在破題與條列；結尾一句用「期待能將…經驗帶進／運用在…」這類語氣，不寫「可以直接投入」「完全符合」「一定能」等過度自信說法，也不寫乞求句。
6. 一封只回應一個職缺；**公司名、職缺名逐字核對 routing.tsv／JD**。

## 4. 產出

- 草稿：`career/letters/104/<code>-<公司>-draft.md`，內容：
  1. 檔頭 HTML 註解：給潤飾者的規則（只改語感、不改事實與數字、保留限定詞、維持 250–350 字、不加 AI 套話）。
  2. 推薦信正文。
  3. 〈對位表〉：每一點對應的 JD 需求 ↔ library 出處（檔名＋節）。
  4. 〈刻意不寫〉：此職缺的已知缺口與處理方式。
- 字數檢查（純文字）；行數只作參考（含稱謂、空行、署名約 12–15 行，桌機一屏可讀完）並寫在檔尾。

## 5. 潤飾後核對與定稿

1. 讀潤飾稿：公司名、職缺名逐字相同；數字、日期、限定詞不變；禁用詞為 0；字數 200–400。
2. 只把語意偏移處回報本人決定；本人同意後存 `career/letters/104/<code>-<公司>.md`（定稿），並在 `career/letters/log.md` 加一列（日期、公司、職缺、語言 zh、檔案、結果〔待填〕）。
3. **登錄職缺關聯（2026-10-27 起必做）**：建立或更新 `career/applications/<code>.md`（職缺代碼、104 連結、`targets/jobs.md` 節號、`review-panel/jd/full/<code>.md`、routing 分層、推薦信定稿與草稿路徑、Codex commit、搭配的履歷版本、投遞狀態，以及**貼入 104 的推薦信全文**與版本紀錄），並在 `career/applications/INDEX.md` 加一列或更新該列。範本見 `applications/8o3s3.md`。不寫進 `targets/jobs.md`（會被重新匯出覆蓋）。
4. 新用到的成果句回填 `letters/story-bank.md`；本人新提供的動機或觀察先寫進 `library/`（about-me 或 facts）。
