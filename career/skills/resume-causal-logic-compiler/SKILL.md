# Resume Causal Logic Compiler

## Core Compiler Rules (嚴格編譯規則)
1. **禁止前向引用 (No Forward Referencing)**：撰寫第 N 個 Bullet Point 時，絕對禁止直接使用第 N+1 個（或更後面）才會首次定義的系統名稱、專案代號或業務背景。
2. **首次提及必定義 (Define on First Use)**：任何內部專有名詞或系統在「第一次出現」時，必須附帶完整的上下文錨點（是什麼系統、服務什麼量級的受眾、解決什麼痛點）。
3. **單點獨立性測試 (Standalone Readability Test)**：假設把其他所有點遮住，只單獨讀當前這一點，外部 HR 也必須 100% 理解前因、動作與量化影響。
4. **敘事起點 LEAD（2026-10-23 取代舊「一律量化成果 (Result) ｜ 核心行動…」）**：依讀者理解所需決定起點與數字位置。
   - `[LEAD: RESULT]`：第一句已交代對象、指標與變化，讀者不必等後文才懂數字意義時採用（如 Peach 網頁付款占比、提案 30 天內結案比例）。
   - `[LEAD: ACTION]`：核心在本人負責的規劃、協作與交付，數字僅為補充交付量或規模時採用（如約 50 項功能上線，將交付量接在需求分析、規格與驗收協作之後）。
   - `[LEAD: CONTEXT]`：必須先理解使用者問題、既有系統限制、服務中斷事件或實驗對照設計，才能理解後續行動與數據時採用（如新版系統 840／743 件建議、199 件即時通與 55 件群組建議、JustDating／Juicy 下架承接、馬來西亞定價實驗）。
   - 產出 `causal_draft.md` 的 `NEEDS_POLISH` 標記時統一寫成：`<!-- [STATUS: NEEDS_POLISH] [LEAD: RESULT|ACTION|CONTEXT] [LOCK_ENTITIES: ...] -->`。
   - 數字放置：需求件數放問題背景旁；交付量接責任與行動；成效數據保留比較口徑及歸因。不強制全篇成果先行，也不一律把數字移到最後。詳見 Codex `voice_style_guide.md` §9。

5. **去日常流水帳、凸顯 PM 功績與破局難度（Impact & Stakes Framing，2026-10-24 本人新增，全篇適用）**：同時嚴守不捏造數據、不跨過 `OVERCLAIM_PATTERNS` 責任禁令。
   1. **禁止純行政與例行事務流水帳（No Chore Lists）**：正文不得單純羅列排甘特圖、送簽、結案確認、每週回報、處理翻譯、新增／編輯／刪除、依主管／公司政策等例行公事；每個動作都要綁定「解決什麼商業或系統限制（Stakes）」或「達成什麼產品與推進目的（Purpose）」。必須交代政策歸屬才能誠實解讀數字時，寫成限制條件（例如「在主管訂定的處理優先序下」），不寫成工作項目。
   2. **把內部專案代號轉成外部懂的戰略規模與破局難度**：例如「新版求才系統」要寫成企業端招募系統的全面翻新改版，交代沿用既有業務後台與底層資料庫、歷史權限與計費規則沒有文件的限制，以及逆向還原規則、重建流程與規格、分階段上線的作法與結果。
   3. **無營收數據的項目，以商業模式完整度／跨端規模／0 到 1 破局展現功績**：不可只列功能名稱或日常任務，要點出商業定位（例：建立涵蓋訂閱、點數與曝光的多元變現機制；統籌 7 個海外市場的產品在地化；在維持既有付費企業服務與新版改版並行的雙線需求下完成功能交付）。
   4. **不用內部行話**：工作中慣用的縮寫或行話（例：「刊案」）對外讀者不直覺，一律改寫成完整說法（例：「刊登合作邀約」）。
   5. **跨欄去重**：同一組成果數字不在全篇重複三次；工作經歷與專案成就（獨立卡片）可並列，自傳只寫判斷與做法（2026-10-24 本人選 B）。
   6. **事實不足就提問**：library 不足以寫出「為什麼有價值／解決什麼困難」時，不硬湊，依 Clarification Gate 向本人提問。

## Execution Workflow
每次修改 `career/01_claude_stage/causal_draft.md` 時，必須先在內部完成：
1. **Phase 1 (Entity Dictionary)**：盤點本次涉及的專有名詞、外部白話定義與首次解鎖位置。
2. **Phase 2 (Topological Sort)**：檢查依賴順序，若前面的點依賴了後面才定義的系統，強制重排順序或將定義前移。
3. **Phase 3 (Verification Gate)**：確認無未知黑話、無 `**粗體開頭：**`、且已正確標註 `<!-- [STATUS: NEEDS_POLISH] [LOCK_ENTITIES: ...] -->` 或 `<!-- [STATUS: LOCKED] -->`。
4. **Phase 4 (Self-Evolving Gatekeeper，2026-10-24 本人新增)**：
   - **三聯同步鐵律**：每當本人在對話中抓出任何事實偏差、日常流水帳寫法（Chore）、被動語態或下游幻覺詞時，嚴禁只修改單點草稿交差，必須同步完成三件事：
     1. **事實層**：更新 `career/library/`（`facts-*.md`／`decisions.md`／`superseded.md`）。
     2. **規則層**：將通用原則補充至 `resume-causal-logic-compiler/SKILL.md`（若涉及下游語氣，同步列出供 Codex 更新 `voice_style_guide.md`）。
     3. **驗證層（強制程式化回歸）**：若該問題可透過關鍵字、正規表達式或結構比對攔截，**必須當下同步更新 `career/scripts/verify_polish.py`**（加入 `CHORE_AND_HALLUCINATION_TOKENS`、`FORBIDDEN_104_TAGS` 或結構檢查），確保同一錯誤在全篇任何角落與未來版本都無法通過腳本。
