# 履歷驗證方式完整說明（2026-10-13）

> 給 ChatGPT 或任何外部審查者用。內容＝本 repo 目前實際在跑的驗證，全部來自 `resume-review-panel`／`resume-craft` skill 與腳本，不是理想化描述。
> **重要限制**：所有「分數」都是**模型模擬**，不是真人意見；真人回饋以 104 的曝光與投遞回覆為準（本檔 §9）。

## 0. 總覽：三種驗證＋兩項輔助

| # | 驗證 | 做什麼 | 誰執行 | 產出 |
| :-- | :-- | :-- | :-- | :-- |
| 1 | **機械檢查** | PDF 能不能被解析、ATS 三項分數、禁用詞、版面結構 | Python 腳本，不用模型 | 通過／不通過＋分數，不判斷內容好壞 |
| 2 | **6 秒 F 型初篩** | 模擬招募者只看到「眼睛掃到的字」，判斷要不要往下看 | 另一個模型（非寫稿者） | JSON：職稱、公司、年資、能不能做、yes 理由、往下看／略過 |
| 3 | **盲審（20 位審查者×5 輪）** | 10 位人資＋10 位用人主管 persona，與對照組、同儕匿名混排評分 | 另一個模型（非寫稿者），5 個獨立 context | 分數、名次、Level、資深類型、數字缺口、紅字用語、面試追問 |
| 輔 A | ATS 搜尋排名 | 模擬招募者在 ATS 資料庫搜關鍵字，看履歷排第幾 | `ats_search.py`（BM25） | Top-10 命中率、平均名次 |
| 輔 B | 事實核對＋真實依據 | 履歷數字對回事實庫；104 曝光／投遞回覆 | 人工＋library | ✅／⚠️／❌ |

**共通原則**：寫稿者≠審查者（換模型、新 context）；審查者看不到事實庫、改稿理由、版本名稱；5 輪取平均與波動；**兩版差距小於波動不算進步**；對照組或同儕 C 沒排在預期位置，這次評分不可信。

## 1. 驗證一：機械檢查（不用模型）

### 1.1 PDF 解析測試（`parse_check.py`）
`pdftotext -layout` 把 PDF 轉回文字，與原稿 txt 比對。

| 項目 | 通過條件 |
| :-- | :-- |
| 文字還原相似度（去空白後 `difflib` 比對） | ≥ 95%（單欄 PDF 實測約 99.6%；雙欄 PDF 會左右交錯，約 55–77%，所以雙欄只給人看） |
| 標題可讀 | 專業摘要、工作經歷、學歷、專業技能、自傳 都能在抽出文字找到 |
| 日期 YYYY/MM 還原 | 原稿每個日期都在抽出文字中（例如 33/33） |
| 亂碼字元 U+FFFD | 0 |
| Email | 抽出文字有 Email |

### 1.2 ATS 分數（`resume_score.py ats`，依 `career/style/ats-2026-source.md`）
A（格式）用 career-ops verify-ats；E（AI 實證）人工；腳本只算 B、C、D：

| 項 | 滿分 | 算法 |
| :-- | :-: | :-- |
| **B 關鍵字對應** | 25 | 關鍵字覆蓋率（履歷全文含幾%的 JD 必備詞＋加分詞）：70–90% → 25；90–95% → 22；≥ 95% → 18（疑似塞詞）；50–70% → 15；< 50% → 8。再乘 (0.6＋0.4×加分詞「同時出現在經歷與技能」的比例) |
| **C 6 秒可讀 v2** | 20 | 8×（條列左緣 10 字有數字或結果／關鍵詞的比例）＋ 4×（條列前 20 字有數字或關鍵詞的比例）＋ 4×（經歷抬頭「職稱在左、日期在 24 字寬內」的比例）＋ 2（摘要沒有求職目標語）＋ 2（前 3 行看得到職稱）。視覺寬度：中文 1、英數 0.5 |
| **D 量化影響** | 20 | 含數字條列比例 ≥ 60% → 20，否則按比例；職責式開頭（主責／負責／協助／參與／處理／管理 開頭）每處 −2 |

額外旗標：「絕對語氣」（每個功能、都由我、一路帶、全部由我、所有功能）與「組織負面」（前任主管未、停擺、推倒、不是主管…）命中即列為 **Level 8 旗標**。

### 1.3 禁用詞（命中即扣）
致力於、深入探討、扮演關鍵角色、成功實現、無縫、編織、Spearheaded、Architected、協助、參與、負責、具備良好、熱情洋溢、賦能、至關重要、不可或缺、值得注意的是、總而言之、展現了、充滿熱情、積極進取、0 到 1、從 0 到 1、0→1、東南亞金流、期許自己、挑戰自我、團隊合作能力、抗壓性極佳；另禁破折號「—」與粗體。使用者另指定不寫：SQL、Jira、Scrum、零停機、JD2（一律寫 JustDating）。

### 1.4 版面結構檢查（`f_scan.py` 無參數模式）
| 項目 | 通過條件 |
| :-- | :-- |
| 前 3 行看得到職稱 | 有 |
| 摘要不是求職目標 | 沒有「希望、尋求、期望、追求、挑戰性、發揮所長」等 |
| 每段經歷抬頭 | 職稱在左；起訖日期落在前 24 字寬內；10 年前且與職缺無關者列為「可刪候選」（使用者裁定保留新蛋） |
| 條列左緣 10 字有結果或關鍵詞 | 目標 ≥ 60% |
| 職責式開頭 | 0 |
| 可推算年資 | 由抬頭日期加總 |

## 2. 驗證二：6 秒 F 型初篩

### 2.1 依據
招募者初篩約 6–10 秒，視線走 F／E 型、集中左緣，先找最近職稱、目前公司、起訖日期（`career/style/hr-6-second-source.md`）。

### 2.2 F 型視野的產生規則（`f_scan.py --view-only`）
| 位置 | 看得到多少 |
| :-- | :-- |
| 上方前 3 行 | 全句（最多 80 字寬） |
| 經歷抬頭（含日期與｜） | 前 24 個字寬 |
| 其餘每一行 | 前 10 個字寬，後面以 … 表示沒看到 |
| 第一屏長度 | 累計約 1,400 字後截斷 |

### 2.3 提示（整段貼給審查模型）
```text
你是台灣軟體業的招募專員，每天看上百份履歷。下面是一份履歷「你在 6 秒內眼睛實際掃到的字」：
上方幾行看得到全句，之後每行只看得到開頭幾個字（…表示後面你沒看到）。
只能根據看得到的字回答，看不到的不要猜；猜不出就寫「看不出」。

目標職缺：{職缺摘要}

{F型視野}

只輸出 JSON：
{"title": "最近一份工作的職稱", "company": "目前或最近的公司", "years": "總年資（數字或看不出）",
 "can_do": "是／否／不確定", "can_do_evidence": "依據哪一句（引用看得到的字）",
 "yes_reasons": ["最多 3 個讓你想說 yes 的理由，每個引用看得到的字"],
 "red_flags": ["讓你想略過的地方"], "read_on": "往下看／略過"}
```

### 2.4 判讀
| 項目 | 通過條件 |
| :-- | :-- |
| 職稱、公司、年資 | 三項都答對（年資差 ±1 年內算對）；**任一答錯＝初篩不過** |
| can_do | 「是」，且依據引用的是成果或職稱，不是自我描述 |
| yes_reasons | ≥ 2 個，且至少 1 個與想傳達的訊息一致 |
| 校準 | 同儕 C 應「略過」或 yes 理由 ≤ 1；否則這輪不可信 |

盲審（驗證三）的資料包會把 6 位候選人的 F 型視野放在「第一關」，先只看視野回答 `triage`，再往下看完整履歷。

## 3. 驗證三：盲審（20 位審查者×5 輪）

### 3.1 設計
1. 用 Agent 另開 context，**換模型**（寫稿者以外：Sonnet 或 Opus；Fable 曾因額度失敗）。
2. 每輪資料包 6 份匿名履歷、亂序：**受測版本 2 份**（新版與前一版或最高分版）＋**對照組 v5.2**（已知較差）＋**同儕 A（好）／B（中）／C（差）**。每輪代號與順序重排。
3. 審查者只拿到：履歷文字、目標職缺（A 級 15 筆職缺高頻詞＋Gogolook Senior PM 代表職缺）、20 位 persona 表。**不給**事實庫、essay、改稿理由、版本名稱。
4. 跑 **5 輪**（5 個獨立 context），彙整平均與標準差。

### 3.3 評分維度
- **人資 H1–H10**、**用人主管 M1–M10**：各 1–5 分整數，分別取 10 人平均。
- 另輸出（見 3.5）：總排名、Level 1–10、資深類型、XYZ、建議刪除、數字缺口、紅字用語、8 題面試追問。

### 3.4 Level 與資深類型定義
| Level | 意義 |
| :-- | :-- |
| 7 | Good：多案例支持面試 |
| 8 | 明確優於同級：另需明確取捨、可比較衡量、限制說明、跨角色一致模式 |
| 9–10 | 頂尖：高度對應目標職缺且量測可追溯 |
| 不確定度 | 一律 ±1 級；只用整數 |

資深類型：**a** 資深交付／**b** PO 跨部門協調／**c** 獨立負責方向與資源。

### 3.6 彙整規則

（表內「A 段」＝第 2 節 6 秒初篩輸出，「B 段」＝3.5 的盲審 JSON。）

| 指標 | 怎麼算 | 用途 |
| :--- | :--- | :--- |
| 初篩通過率 | A 段三項答對且「往下看」的輪數 ÷ 5 | 版面是否撐得過 6 秒 |
| 平均 yes 理由數 | A 段 yes_reasons 個數平均，另記與 essay「yes 理由」一致的數量 | 第一屏是否傳達了想傳達的事 |
| XYZ 完整條列比例 | B 段 xyz 三格皆 true 的條列 ÷ 總條列 | 成果寫法 |
| 職責條列數 | B 段 type＝職責 | 應為 0 |
| 只有做法的條列 | B 段 type＝只有做法，每段 ≤ 1 | 交付鏈例外是否用過頭 |
| 建議刪除 | B 段 cut，5 輪中 ≥ 3 輪出現才列 | 相關性刪減 |
| Level（v3.2） | B 段 level 的中位數與範圍 | 兩版中位數差 < 1 級視為同級 |
| Senior 型（v3.2） | B 段 senior_type 眾數 | 是否出現 c 型證據 |
| 數字與用字（v3.2） | number_hygiene、red_wording，≥ 3 輪才列 | 回步驟 2 補口徑或步驟 5 改寫 |

規則同 v3：5 輪平均與波動；**兩版差距小於波動不算進步**；對照組或 C 級同儕沒排在預期位置，這次評分不可信。

額外規則（v3.2，採納外部 ChatGPT 審查）：絕對分數會飽和、系統性高估，**不解讀 1–2 分的差**，以名次、Level（±1 級）與分項證據為主；PDF／ATS 解析、AI 來源判讀、真人招聘效度**分開判斷**，不合成一個分數。

## 共通審查清單（人資版）
1. 7–10 秒內能不能看出：**職稱、年資、最近一份工作、是否符合必備條件**。
2. 時序：起訖是否連續、有無空窗與原因、每份是否 ≥ 2 年。
3. 可信度：數字有沒有基準、是否誇大、是否前後一致（摘要、經歷、自傳）。
4. 可讀性：非技術人員能不能看懂每一條在做什麼。
5. 軟實力：有沒有「和人相處」的行為證據（帶人、說服、處理衝突），而非形容詞。
6. 語氣：是否像本人寫的（AI 腔、空泛詞、句型一致）。
7. 自傳：500–1,000 字、有個人動機與共事方式，不是第二份履歷。

## 共通審查清單（用人主管版）
1. **範圍與資深度**：負責的產品面、使用者或營收規模、團隊大小、決策層級（不只年資）。
2. **成果與因果**：有基準、有做法、有結果（XYZ）；分清楚「我做的」和「團隊做的」。
3. **取捨與判斷**：有沒有砍範圍、說「不做」、在模糊中下決定的例子。
4. **與職缺的相關性**：產業、產品型態（B 端／C 端）、0→1 或優化、技術深度是否對得上。
5. **軟實力**：說服、帶人、處理衝突、跨文化、對使用者的同理——要有情境證據。
6. **可面試性**：每條都能延伸出好問題；誇大或術語用錯會在面試被拆穿。

## 5. 輔助 A：ATS 搜尋排名（`ats_search.py`）
ATS 多半是讓招募者「搜尋」的資料庫。做法：從 A 級職缺推導招募者會打的查詢詞（每職缺 3 組）；把各版本分別放進 **50 份同儕履歷**索引（版本之間不互相競爭）；以 **BM25** 排名（中文用字元 bigram、英數用單字切詞；k1=1.5、b=0.75）；輸出每條查詢的名次、各版本 **Top-10 命中率、Top-3 命中率、平均名次**。

## 6. 輔助 B：主管模擬面試與事實核對
- 盲審同時產生每份 8 題追問；逐題對照 `career/library/` 能不能作答，答不出來的條列標為**面試風險**。
- 事實核對：履歷數字逐條對回事實庫，標 ✅有證據／⚠️措辭超過證據／❌找不到證據；對照 `superseded.md`（已作廢說法）命中即 ❌；交付鏈（Journey、User Story、Use Case、SA、流程圖、Wireframe、Prototype、Spec、與工程追時程、QA、上線計畫）任一段完全缺席視為不通過。

## 7. 判讀鐵則與已知限制
1. 差距小於 5 輪波動不算進步；校準失敗（同儕 C 沒墊底、對照組位置異常）整次作廢。

6. 本 repo 的 AI 作者辨識**不可靠**，不做；自然語氣只檢查文字特徵（禁用詞、對仗、三連排比）。
