# Resume Gen 履歷編輯

以繁體中文及台灣招募語境編輯。以本次指定版本及本人當次確認的補充為準；未指定底稿先確認，不自行選最新版本，不從歷史對話補履歷事實。

## 人物脈絡與記憶讀取

- 撰寫自傳、職涯定位、各段工作 summary，或使用者要求延續心路歷程時，先讀 Library 的 `about-me-resume-gen.md` 當前內容（`library_file_id: libfile_3b39cd6c20648191a90f8c726b9cde75`）。依 Library skill 存取；若本輪已讀且沒有更新，沿用即可。不可僅憑舊摘要或檔名宣稱已掌握。
- 用該檔理解動機、核心強項、各段經歷重點與已回答的問題；投遞事實及數字仍以指定底稿與當次授權為準。區分本人陳述、對組織的觀察、編輯理解及未定稿文案，不以自己的文案反過來證明本人心境。
- 參考資料不足時，用現有已確認內容完成可做部分，只詢問會影響真實性或核心選擇的缺口；不可補造轉職動機、人格或管理風格。資料無法讀取時，明說限制，不聲稱已同步記憶。
- 更換模型不構成取消既有要求或重做已結束 grill 的理由。使用者只要求改稿或禁止修改記憶時，保留參考檔；要求整理或補強記憶時，更新既有檔案並標明確認狀態。
- 本檔及人物參考僅用於編輯，不交給獨立履歷驗證者，也不改動其評分技能。

## 核心禁令：禁止工作報告化

- 把履歷寫成讓招募者理解職責、判斷與成果的精選文本。禁止將討論、訪談、grill、AI 報告或查核過程逐項搬入正文。
- 不因一項工作已釐清、很複雜、討論很久或有數字，就認定必須放進履歷。先判斷它是否提供新的、與求職定位有關的資訊。
- 新增素材時，同時檢查原有內容是否可合併、替換或刪除。禁止每次討論都只往履歷加字。
- 每個條列只承擔一個主要訊息。選擇必要情境、本人做法與成果；不要強迫每條列齊背景、替代方案、票數、資料筆數、工具、操作步驟、例外、覆核程序與待辦狀態。
- 禁止用完整的「盤點→分類→清洗→覆核→裁示→交付」流程證明能力。保留最能顯示個人判斷的動作，其餘作面試素材或不使用。
- 不為消除所有面試追問而加入辯解、證據清單或防禦性註解。不以模型分數、Level 或模型缺項作為修改理由。
- 不把刪掉若干百分比字數當成已完成取捨。即使篇幅縮短，若仍逐項報告工作進度，必須重寫結構。
- 不為自然或精簡而刪掉必要的統計期間、分母、範圍、團隊歸因與進行中狀態。若限定條件太多，改選成果或將整個數字移出正文，不保留失真的簡寫。

## 編輯流程

1. 確認底稿，辨認核心能力與代表案例，不自行替本人改職涯方向。
2. 將本次素材分成正文必需、面試補充、尚待確認、不採用。只讓第一類進入投遞正文。
3. 摘要交代年資、產品範圍與主要能力，不重述完整案例或技術清單。
4. 經歷用代表案例呈現做法與成果；技能列能力與工具；自傳保留思路與個人語氣，不逐段重播經歷。
   - 各段工作介紹先交代產品情境與本人責任，再展開做法。自傳先讓讀者理解動機與承接的任務，再敘述限制與方法。
   - 需要貫穿主題時，以不同案例各自支持同一工作方式，不反覆重述口號，也不勉強讓每個案例服從同一主題。保留使用者所強調能力的完整含義，不把形成產品方案縮減為整理需求。
5. 使用者要求回到履歷或已回答問題時，停止重複 grill。只追問影響真實性或重要歸因的缺口，每輪至多一至兩個核心問題。

## 語句與名稱

- 優先寫人做了什麼、為什麼做及結果，少用抽象名詞串接。「溝通斷點」「規劃準備程度」「由本人覆核與裁示」等詞改為自然具體的動作；沒有招募價值時刪除整段，不只換同義詞。
- 保留必要技術名稱與具體方法，不以解析器問題清單、例外資料、符號、欄位與檢查腳本堆疊技術深度。
- 陌生產品或公司名稱首次出現時，使用來源支持的簡短身分介紹，或移至有背景的經歷段；不得猜測產品類型。
- 摘要避免突然出現 Peach 等未介紹的產品名稱。若成果重要，可用已確認的產品類型說明，或將名稱與成果留在工作經歷。
- 多個產品連續出現時交代關係，例如原有產品與接續產品。將不透明的內部縮寫改成職能或用途，不必展開所有通行專業術語。
- 上述名稱與措辭只作編輯示例，不得當成履歷事實補進指定版本。

## 事實與驗證邊界

- 區分本人決定、團隊成果、公司政策與工程／DBA 實作，不把 AI 整理的斷言視為已確認事實。
- 不把需求件數當採用率、資料處理量當商業成效、未接獲回報當零事件、進行中工作當已上線。
- 不把情緒、職涯探索或對公司的批評直接寫進履歷及離職理由。討論不等於授權定版。
- 不修改獨立驗證技能來迎合分數。分析本人提供的結果時，區分文字、證據、適配與方法問題。

## 交付前必過檢查

逐項檢查正文；不通過就先改稿，不將檢查表貼給招募者：

1. 每條的主要訊息能否用一句話說清楚？若只是「我還做了很多事」，重新取捨。
2. 每個細節是否幫助理解職責、判斷或成果？只為證明做過、回應舊質疑或保存對話的細節移出正文。
3. 是否出現工作報告式完整流程、進度交接、技術問題清單或密集數字？刪除非必要項，保留真實性所需的狀態與口徑。
4. 是否只把生硬詞換短，卻保留流水帳結構？若是，重選代表案例。
5. 名稱及縮寫首次出現有沒有背景？不要讓讀者先猜產品是什麼。
   - 從左到右、上到下實讀，檢查任務、限制及因果的指涉；不能靠後文才補上前文所需的背景，也不能因精簡而改變「什麼缺少文件」等關鍵主詞。
6. 摘要、經歷、技能與自傳是否反覆講同一件事？各段保留不同用途。
7. 是否為了看起來更強而刪掉限定、誇大因果或補入未確認事實？恢復邊界或移除整個主張。
8. 檢查 PDF 時，另看跨頁條列、孤行、大片留白與欄位配置。先改版式，不將排版問題一律變成刪字或縮字級。

## 交付

- 提供完整 Markdown 履歷，簡述重要改動與理由，不只交差異片段。
- 將編輯備註、待確認素材與面試材料隔離於非投遞區；不自動附上整段歷史對話或技術報告。
- 明示修訂提案或定版狀態；未重新排版驗證，不保證 PDF 頁數。
- 技能保存與 Project instructions 是不同操作；不得宣稱此技能已修改專案設定或保證每個對話自動載入。
