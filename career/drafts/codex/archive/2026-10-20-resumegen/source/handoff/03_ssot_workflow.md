# SSOT 導入建議與交接規則

以下是給接收端的可執行整合建議，尚未套用到使用者的 Claude Code 專案，不代表已完成 SSOT 遷移。

## 先整合既有專案

1. 讀既有 AGENTS.md、CLAUDE.md、技能與資料結構，記下現行工作稿及目前未提交變更。不要把本包直接解壓後覆蓋專案根目錄。
2. 本包先放在一次性的 migration/archive 區；以 SOURCE_MAP.json 與 SHA256SUMS.txt 辨認相同內容及不同版本。
3. 合併同用途參考檔，保留來源與確認日期。不要把較新修改時間當成本人已確認，也不要從所有舊履歷抽取數字自動建立事實總表。
4. 本人下一次指定工作底稿後，將唯一工作檔路徑寫進專案狀態。履歷正文、自傳與後續 PDF 都由該檔衍生。

## 每一類資料只有一個維護位置

| 資料 | 接收端應維護的唯一位置 | 使用規則 |
| --- | --- | --- |
| 當前工作稿 | 專案狀態指向的一份 Markdown | 由本人指定；封存包不替本人指定 |
| 已確認事實與數字 | 若既有專案有事實檔則沿用該檔 | 記本人來源、期間、範圍、定義與確認狀態；不要從歷史版本自動回填 |
| 人物脈絡與寫作偏好 | 一份 About Me | 先與本包第四版對照，再依本人新確認更新；不複製成兩套有效設定 |
| 編輯規則 | 共同參照的一份規則／技能來源 | AGENTS.md 與 CLAUDE.md 以簡短引用導向同一份規則，避免各自存整套易分歧版本 |
| 衍生 PDF | 由指定文字稿輸出 | 記錄輸入稿的 hash、排版來源與輸出 hash；PDF 不反向取代文字事實 |
| 歷史檔案與對話 | 封存區 | 可追溯但不直接覆蓋現行內容；對話不自動成為送驗輸入 |
| 獨立驗證輸入 | 另建乾淨封包 | 僅指定履歷、職缺、規準，與完整編輯檔案分開 |

檔名與目錄可沿用接收端既有設計；重點是共同指向同一份來源，無須為了遷移建立第二個平行專案。

## Codex 與 Claude Code 的寫入協調

- 每次工作開始都從共同狀態讀取目標檔、分支／提交與當前 hash，不只參考自己的對話。
- 指定此輪唯一寫入者與範圍。另一端做閱讀、檢查或在獨立分支提出修改，不同時直接寫同一檔案。
- 修改前後保留版本差異，確認另一端是否已更新。同一欄位出現衝突時，保留兩側依據並依本人確認處理，不能用最後寫入者勝出。
- 完成時一次更新工作稿、必要參考與變更紀錄，說明修改原因及依據。使用者只授權改稿時，不順便更新 About Me 或規準。
- 頁數與版面有問題，先調整排版；若文字需要取捨，再依事實與閱讀需求提出修改，不以分數或縮頁作唯一目標。

## 對話匯入

收到使用者的全量匯出後，先原樣保存並編目。對話用來追溯確認、撤回與解釋，助手的建議不能因被多次引用就變成已確認事實。只把會影響當前工作且獲授權的結論合併到維護中的資料。

本包不需要使用者重做既有問答。只有來源衝突且會改變正文時，才聚焦詢問一至兩個問題。
