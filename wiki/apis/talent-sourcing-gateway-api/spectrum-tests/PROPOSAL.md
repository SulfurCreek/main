# 三情境光譜測試規格（給執行模型的完整 requirement & outcome）

> 產出：2026-07-20，已經使用者核准。執行模型照本檔執行即可，毋須重新設計案例。
> 執行前置：需向使用者取得 `TSG_API_ID`／`TSG_API_KEY`（僅存 shell 環境變數，不落地）。

## Context

Talent Sourcing Gateway API（spec：`wiki/apis/talent-sourcing-gateway-api/spec/talent-sourcing-ateway-api_v1.0.1@20260717.yaml`）已完成基礎測試與 41 筆 104 URL 批次呼叫。現要進行三種情境、各 100 案的光譜式測試：

| 情境 | 輸入 | 核心驗證目標 |
| :--- | :--- | :--- |
| S1 競品 URL | 104 職缺頁 URL × 100（spec 僅支援 104/1111，其他競品站不納入，使用者已確認） | `url` 模式大量真實職缺的成功率、schema 一致性、解析穩定度 |
| S2 競品 URL＋文字 | 104 職缺 URL＋補充徵才需求文字（光譜：歧視性條件 → 純技能條件） | `url_text` 模式下補充文字如何影響推薦；歧視性文字是否原樣進入 `query_used`（法遵觀察） |
| S3 純文字 | 徵才需求描述（光譜：乾淨結構化 → 轉述式＋複合敏感條件） | `text` 模式的解析穩健度、零結果 suggestion 行為、敏感條件的處理 |

**spec 前提**：query 僅支援 104 與 1111 職缺網址。競品 URL 一律取 **104 職缺頁**；518/CakeResume 不使用（使用者已確認排除）。

**倫理/法遵註記**：S2/S3 光譜中含就業服務法第5條禁止之歧視性條件（年齡、性別、婚育、容貌等），**僅用於測試自家 API 對此類輸入的行為**（是否過濾、改寫、照單全收），供產品法遵設計參考，不用於任何實際人才篩選。

## 一、執行環境需求（executor requirements）

1. 憑證：`TSG_API_ID`／`TSG_API_KEY` 環境變數（僅存當次 shell，**不寫入任何檔案**）。Base URL：`https://$TSG_API_ID.execute-api.ap-northeast-1.amazonaws.com/dev`，endpoint `POST /v1/recommend`，`client_id` 固定 `1111productpm`。
2. 逐案循序呼叫，每案間隔 ≥1 秒（總計 300 次呼叫，含下游 TalentRecommendation 成本，預估 20–40 分鐘）。timeout 60 秒。
3. **不自動重試**；timeout／connection error／非預期狀態碼照實記錄該案後繼續下一案。每案寫檔即 flush（中斷時已完成部分不遺失）。
4. 產出檔案（放 `wiki/apis/talent-sourcing-gateway-api/spectrum-tests/`）：
   - `cases_s1.json`／`cases_s2.json`／`cases_s3.json`：輸入案例（含 case_id、band、query、expected）
   - `results_s1.json`／`results_s2.json`／`results_s3.json`：陣列，每元素＝`{case_id, band, query, expected, http_status, error_code|null, response}`（response 為原始 body）
   - `summary_s1.json` 等：機器彙總（見附錄 C 欄位），**不寫散文報告**
5. case_id 規則：`S1-001`…`S1-100`、`S2-001`…、`S3-001`…。

## 二、S1 競品 URL（100 案，全部 104 職缺頁）

### URL 蒐集需求（執行者自行上網蒐集，執行當天驗證有效）

- 數量：**100 個相異的 104 職缺頁 URL**。格式：`https://www.104.com.tw/job/{5碼英數}`（可帶 `?jobsource=` 參數）。
- **只收職缺內頁**；不可是公司頁 `/company/…`、搜尋/列表頁 `/jobs/search/…`、主題頁。判別：URL path 必為 `/job/{code}`，頁面含職缺標題與「應徵」按鈕。
- 每個 URL 在執行當天先以 HTTP GET 確認職缺存活（避免下架職缺造成 404 JOB_NOT_FOUND 混入干擾；若刻意保留 1–2 個下架 URL 需標記為預期 404）。
- 職缺類型盡量分散（工程／行銷／門市／製造／醫護／設計／餐飲／物流…），地區分散北中南；此 100 個 URL 之後供 S2 一對一重用作 baseline。
- 可沿用既有 41 筆（見 `104-batch-responses_20260720.json` 內 `metadata.source.url`，去重後約 40 個），再補足至 100。

### 每案預期結果（outcome）

| 項目 | 預期 |
| :--- | :--- |
| HTTP | 200 |
| 欄位 | `input_mode=url`、`source.type=104`、`source.job_id`＝URL 路徑碼、`query_used` 含【來源職缺需求】段 |
| Schema | 通過 RecommendResponse schema；`recommendations` 依 rank 升冪；`result_count`＝筆數 |

異常判定：404 `JOB_NOT_FOUND`（存活驗證通過卻 404 ＝ 解析問題，重大發現）、5xx／timeout（下游異常，逐案記錄）、200 但 `source.type≠104`（辨識錯誤）。
