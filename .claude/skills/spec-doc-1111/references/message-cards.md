# 訊息泡泡／邀約卡片：雙視角互動規格

> 屬 `spec-doc-1111` skill 的參考檔。**只有在撰寫聊天室訊息／邀約卡片類規格時才需要讀**（如 HackMD `訊息樣式`、E.1 聊天室訊息區）。

聊天室訊息、邀約卡片（Interview Card：詢問意願／面試邀約／錄取通知／感謝函）這類**跨系統、同一則訊息在收發兩端各有不同呈現**的規格，不照「初始化 → 編號區塊」骨架走，改用以下雙視角寫法（範例見 HackMD `訊息樣式`）。

### 1. 每個訊息／邀約類型開頭：卡片內容定義表

H3 為訊息類型，開頭先用一張表定義卡片「主旨／判斷條件／資訊區塊／欄位／按鈕」結構，多欄位用 `<ul><li>`：

```markdown
### 面試邀約

| 訊息主旨 | 資訊區塊 | 資訊欄位 | 泡泡內按鈕 |
| :--- | :--- | :--- | :--- |
| `面試邀約` | 面試資訊 | <ul><li>面試地點</li><li>面試時間（可多筆）</li><li>回覆期限</li><li>聯絡人</li><li>電話</li></ul> | <ul><li>改時間</li><li>取消面試</li></ul> |
```

**判斷條件欄位（新舊代碼共存時）**：當同一個業務類型在前後端歷史演進中對應到不只一組代碼（例如新版用單一 `Type`，舊資料是 `Type`+`InterViewKind` 組合），欄名用 `判斷條件`（不要只寫 `Type`），欄內用 `<ul><li>` 列舉現行代碼 + 各組「舊資料：」相容代碼，**不要**因為有多個值就誤判成需要 🚧 待補規則的衝突——這是已確認的新舊相容規則，直接列出即可：

```markdown
| 訊息主旨 | 判斷條件 | 訊息區塊 |
| :--- | :--- | :--- |
| `詢問意願` | <ul><li>`Type(MailType):2`</li><li>舊資料：`Type(MailType):1`&`InterViewKind:0`</li><li>舊資料：`Type(MailType):8`&`InterViewKind:0`</li></ul> | 廠商輸入的訊息<br>`message` |
```

> 與 🚧 待補規則的分界：**已確認**的新舊代碼相容關係 → 判斷條件欄位列舉；**尚未確認**、需要 PM 裁示哪邊為準的矛盾 → 才用 🚧 待補規則區塊（見下方該節）。

### 2. 拆成「發出 ↔ 收到」兩個視角（H4）

同一類型拆成兩個 H4，分別描述發送端與接收端；泡泡靠邊與角落資訊位置隨視角相反：

| H4 | 泡泡位置 | 角落資訊欄名 | 卡內按鈕 |
| :--- | :--- | :--- | :--- |
| `#### 廠商發出：{類型}` | 靠右 | `右下角資訊` | 廠商可改/取消的操作鈕，或無按鈕 |
| `#### {對方}收到：{類型}` | 靠左 | `左下角資訊` | 對方可回覆的 `同意`／`婉拒` 等按鈕 |

> 標題用「動作＋冒號＋類型名稱」（如 `廠商發出：詢問意願`），不要把動作與類型直接黏在一起（舊文件 `廠商發出詢問意願` 寫法停用）。

每個視角 H4 開頭放一張「截圖／泡泡內按鈕／角落資訊」表（角落欄名隨視角寫 `右下角資訊`／`左下角資訊`，內容用 `<ul><li>`）。**若同一視角下有多個明確的互動結果狀態**（如初始／已同意／已婉拒），直接在這張表多加幾列、每列截圖前標明狀態名稱，不要另外拆成段落散文描述：

```markdown
#### 求職者收到：詢問意願

| 截圖 | 泡泡內按鈕 | 左下角資訊 |
| :--- | :--- | :--- |
| 初始狀態![image](https://hackmd.io/_uploads/xxx.png) | <ul><li>同意按鈕</li><li>婉拒按鈕</li></ul> | <ul><li>發送時間</li><li>hover 提示</li></ul> |
| 求職者同意![image](https://hackmd.io/_uploads/yyy.png) | 同意按鈕disabled | 同上 |
| 求職者婉拒![image](https://hackmd.io/_uploads/zzz.png) | 婉拒按鈕disabled | 同上 |
```

### 3. 「點擊按鈕後的狀態」固定 cascade

接收端可回覆的卡片，按鈕之後用 `**點擊{按鈕}後的狀態**` 粗體小節，依固定順序描述連鎖結果：

```markdown
* **點擊按鈕後的狀態**：
  * 保留被點擊的按鈕、其餘按鈕轉 disabled（不可重複回覆）
    <img style="max-width:250px" src="..."> <img style="max-width:250px" src="...">
  * 寫入訊息與資料：
    * 依回覆帶入預設文字寫一則[一般訊息](#一般訊息)回覆，以對方身分發出並即時顯示
    * 新增一筆[意願狀態標籤](#意願狀態標籤)（有意願＝綠／婉拒＝灰）
    * 更新對話的意願狀態
  * 畫面即時更新
  * 後端寫入與通知詳見 [跨系統流程與後端邏輯](/{noteId})
```

要點：

- **按鈕點擊後一律 disabled**、保留被點按鈕，避免重複回覆。
- 多個結果狀態的截圖**並排內嵌**（`<img style="max-width:250px">` 接連寫），不另開區塊。
- **後端寫入／signalR／推播不在本文展開**，一律連結到獨立的「跨系統流程與後端邏輯」文件（見第 5 點），避免每個訊息類型重複貼後端步驟。

### 4. 意願狀態標籤：雙視角文案差異

系統依操作自動寫入、雙方都看得到的提示文字（意願狀態標籤），**同一則在兩端主詞不同**，必須兩端文案都給，不要只寫一端：

- 廠商側用第三人稱主詞：`施小君已回覆有意願面試`
- 求職者側用第二人稱：`你已回覆有意願面試`
- 樣式：有意願／同意＝綠色；無意願／婉拒＝灰色。

### 5. 後端邏輯獨立成文件

跨系統的寫信件主表／寄 E-mail／signalR／推播／面試行事曆等後端步驟，集中放在**一份獨立的「跨系統流程與後端邏輯」note**，各訊息類型在「點擊後狀態」末尾用相對連結 `[跨系統流程與後端邏輯](/{noteId})` 指過去；不在每個訊息類型內重複展開，也不混進畫面規格。
