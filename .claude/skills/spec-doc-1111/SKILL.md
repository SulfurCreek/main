# 1111 規格書撰寫格式（spec-doc-1111）

本 skill 封裝 1111 人力銀行 recruit 專案在 HackMD 上的功能規格書格式慣例。目標是讓產出的規格文件在結構、編號、樣式、
用語上都與既有文件（如 `B.4 刊登設定`、`3.2.6 AI推薦人才名單`）一致，QA 與 RD 可無縫接續閱讀。

本檔放**每份文件都會用到的骨架與規則**；細部慣例按需載入 `references/`：

| 需要什麼 | 讀哪份 |
| :--- | :--- |
| 版控說明格式、圖片寬度、摺疊區塊、表格慣例、條件邏輯句型、樣式術語 | [`references/styling.md`](references/styling.md) |
| 跨文件引用三層方式、🚧 待補規則區塊、階段拆分 | [`references/cross-doc-and-gaps.md`](references/cross-doc-and-gaps.md) |
| mermaid 流程圖配色與寫法 | [`references/mermaid.md`](references/mermaid.md) |
| 完整骨架範本（直接複製開始填）| [`assets/template.md`](assets/template.md)（求才）／[`assets/template-jobseeker.md`](assets/template-jobseeker.md)（求職）|

## ⚠️ 先確認專案，再選範本（必做第一步）

1111 有**兩個系統、兩套文件範本**，格式差異很大，動筆前必須先確認文件屬於哪個專案：

| 專案 | 對象 | 範本 |
| :--- | :--- | :--- |
| **求才系統**（recruit）| 廠商端（B 端），如 `B.x`、`C.x`、`E.x` 系列 | `assets/template.md` |
| **求職系統**（求職主網）| 求職者端（C 端）| `assets/template-jobseeker.md` |

**判別方式**（依序）：① 使用者明講專案名稱 → ② 文件所在的 HackMD 資料夾（見 `tree.md`）→
③ 功能對象（廠商操作刊登／聯繫人才／合約 → 求才；求職者搜尋職缺／投履歷 → 求職）→ ④ 仍不確定就**問使用者，不要猜**。

**兩套範本的主要差異**：

| | 求才系統 | 求職系統 |
| :--- | :--- | :--- |
| 標題下方 | `User Story:` + `Use Case:` 各一行 | 無 |
| 摺疊區標題 | `:::spoiler Document info` | `:::spoiler 文件資訊` |
| 文件資訊欄位 | 版本／更新／作者／狀態／功能位置 | 同左，但「文件狀態：規劃中／已發佈」、版控表標題用反引號 |
| 主要章節 | `## 示意圖` → `## 初始化` → `## 1.{區塊}` 編號章節 | `## 網址路徑` → `## 介面規格`（`:::info` 摘要 + `### {區塊}`）→ `## 設計稿` |
| 區塊內容標籤 | MECE 四狀態表、權限表格 | `` `功能樣式` `` 與 `` `資料來源` `` 兩段 |
| 設計稿連結 | 無固定章節 | 固定 `## 設計稿` 章節放 Figma 連結 |

下文詳細慣例**以求才系統為主**；寫求職系統文件時以 `assets/template-jobseeker.md` 骨架為準，樣式慣例
（反引號欄位、紅字變更、兩空格縮排、mermaid）仍通用。

## 何時使用

- 從零撰寫某功能的規格書
- 把設計截圖、口語需求、會議記錄轉成正式規格
- 依 QA／RD 回饋修改既有規格（改章節、補狀態情境、標紅字新需求）
- 補上流程圖、版控紀錄、欄位判斷邏輯
- 整理既有文件中散落的權限判斷，重整為標準初始化格式

## 核心原則

1. **狀態／情境驅動**：以「判斷某狀態 → 顯示某樣式／行為」描述，少用散文，多用條列與判斷分支。
2. **欄位即真相**：所有 DB 欄位、旗標、權限代碼、狀態值一律用反引號，例如 `organs.showfield&4096`、`oStatus:1`、`代碼9`、`status = 0,2,4,5,6`。
3. **變更必標紅**：新需求或這版調整的內容用紅字包起來，讓 RD/QA 一眼看出差異。
4. **格式穩定**：未變更的區塊不要動排版、縮排、圖片、編號——保持可 diff。
5. **MECE 狀態涵蓋**：涉及**非同步資料載入**的區塊（初始載入、列表、搜尋、Tab 切換）必須完整涵蓋
   `載入中`／`有資料`／`無資料`／`錯誤`；純靜態區塊（固定標題、固定按鈕）不需要。

## 文件骨架

**直接複製 [`assets/template.md`](assets/template.md) 開始填**（求職系統用 `assets/template-jobseeker.md`）——
那份是骨架的單一真相來源，不要另外憑記憶重打。章節順序為：

`# {代號} {功能名稱}` → User Story／Use Case → `:::spoiler Document info`（版本／更新日／作者／狀態／功能位置／
版控表／`[TOC]` 全包在同一個 spoiler）→ `## 示意圖` → `## 初始化` → `## 1.{區塊}` 起的編號章節。

填寫時注意：

- `MD033`／`MD013` 兩行固定放最上方（文件大量使用 `<font>`、`<img>`、`<ul>` 等標籤）。
- 標題代號形如 `B.4`、`A.2`，與功能模組對應。
- User Story 從 Persona 角度、Use Case 從系統角度，內容包反引號；Use Case 可多條子彈（如跨系統情境分開列）。
- 文件狀態用彩色 span：已發布藍色、草稿灰色；結尾的 `</h6>` 沿用既有文件寫法。
- 功能位置 URL 用角括號包起來自動連結。
- `## 示意圖` 直接嵌入 wireframe，**禁止放外部 URL**；沒有則標示 `` `待補` ``。
- **特別提醒**：list 每一層縮排**必須用兩個空格**（不是一個、不是 Tab），HackMD 才會正確識別巢狀層級。這是最常見的錯誤。

## `## 初始化` 內部結構（重要）

`初始化` 固定是第一個 H2 章節，不編號，固定包含三個 H3 子節：

**`### 進入路徑`** — 列出所有能進入此頁的路徑。只有一個進入點時可省略此節，在 初始化 intro 說明。

**`### 權限判斷`** — **所有廠商與帳號的權限／先決條件判斷一律集中在此節的表格內**，不得散落在後續章節的 bullet 或紅字。

```markdown
| 權限條件 | 代碼 | 不符合時的處理 |
| :--- | :---: | :--- |
| 廠商不得為黑名單屬性 | `confirmed&4096` | 顯示 Alert，點擊後返回首頁 |
| 帳號需有職缺管理權限 | `代碼54` | 隱藏操作按鈕，僅顯示唯讀狀態 |
```

代碼欄位一律用反引號；「不符合時的處理」寫明使用者看到什麼（Alert 文案、跳轉去哪、哪些元素 disabled）。
完整代碼定義見共用參考文件 `[REF] 求才系統權限代碼表`（`/B1j3sN-bzx`）。

**`### 資料載入`** — 頁面進入時撈哪些資料、呼叫哪些 API（或 DB 查詢），以及 `@media` 斷點規則。

## 章節編號階層

編號採**點分式**（`1.1`、`1.2.2`），由大到小：

| 層級 | Markdown | 用途 |
| :--- | :--- | :--- |
| 大區塊 | `### 1 聯絡人才` | 對應頁面主要區塊，從 1 開始；`初始化` 不編號放最前 |
| 子區塊 | `### 1.1 篩選 Tab` | 對應畫面元件群 |
| 元件細項 | `#### 1.2.1 搜尋訊息` | 對應單一畫面元件 |

- 編號要與設計圖標號一致，讓 RD/QA 對照畫面。
- 錨點連結用編號＋標題去空白：`[1.1 篩選 Tab](#1.1-篩選-Tab)`。
- 內文引用其他子區塊直接用反引號編號：`` 詳見 `1.3.5` ``。

## MECE 狀態涵蓋

涉及**非同步資料載入**的區塊必須覆蓋四種狀態；純靜態子區塊（固定標題、固定按鈕、lightbox 欄位說明）**不放**此表，
避免文件臃腫：

```markdown
| 狀態 | 觸發條件 | 畫面呈現 |
| :--- | :--- | :--- |
| 載入中 | 搜尋送出、切換tab、結果回傳前 | 列表區顯示 loading狀態 |
| 有資料 | 取得回傳資料 | 依資料渲染對應區塊 |
| 無資料 | 無命中 | 顯示 Empty State（文案 `待補`） |
| 錯誤 | API 失敗 | 顯示錯誤 toast（文案 `待補`） |
```

此表替代「無資料時顯示空值狀態」散落在各 bullet 的寫法，確保 QA 能系統性驗收。文案未定時標 `` `待補` ``。

## 修改既有規格時

1. **只動相關處**：未提到的章節、圖片、縮排、編號一律不動，維持可 diff。
2. **變更標紅**：新增／調整的需求用 `<font style="color:red">` 包起來。
3. **整理 `初始化` 時**：把散落各章節的權限 bullet 集中到 `### 權限判斷` 表格，原位留下「詳見初始化 → 權限判斷」的錨點連結，**不得直接刪除**。
4. **連動檢查**：改了某情境，同步對應的 mermaid 流程圖分支與交叉連結，避免圖文不一致。
5. **版控紀錄**：每次發布新增一列，調整說明格式為 `[異動區段] 內容摘要`。版號採 `主.次.修` 三段。
6. **不確定就標註**：需求有歧義時，先依合理解讀套用並在交付時明確標出假設，請對方確認。
