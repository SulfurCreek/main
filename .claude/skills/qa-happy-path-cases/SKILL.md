# QA Happy Path 測試案例撰寫

## 範圍鐵律

- **只寫主要成功情境**：使用者用最常見、最理想的方式操作，一路走到底、沒有中斷、
  沒有錯誤，一次就能達成目的。
- **不要自己加**：邊界值（字數上限/最小值）、必填欄位留空、格式錯誤、權限不足、
  併發衝突、逾時、第三方服務失敗等——這些是「異常路徑」/「邊界測試」的範圍，
  屬於另一種任務。使用者只說「happy path」時，寫了會被當成沒聽懂需求。
- 一個功能如果有多條**不同但都算成功**的主線（例如「全職」與「立即上工」兩種
  情境，UI 完全不同），每條各算一個獨立 happy path 案例，不要塞成同一案例的分支。

## 案例來源

1. **HackMD 規格書連結**：先讀該文件（依本 repo `spec-doc-1111` skill 的章節慣例，
   Use Case／情境類段落通常在 `## Use Case` 或帶編號的情境小節），抽出「正常操作
   下，使用者從進入到完成的完整路徑」；業務代碼（`confirmed`／`showfield` 等）不要
   複製定義，用連結指回 `[REF] 系統代碼表`（見 `wiki/recruitment_system_rules.md` §2）。
2. **使用者口述的功能流程**：直接依對話內容整理，不要求對方先寫成規格書。

資訊不足以判斷「怎樣算操作完成」時，直接問使用者，不要自己猜一個預期結果。

## 輸出格式

一個功能（或一條 happy path 主線）一張表：

```markdown
### TC-01｜{情境名稱}

| 步驟 | 操作 | 預期結果 |
| :---: | :--- | :--- |
| 前置條件 | {進入這個流程前，環境/資料/權限需具備什麼} | — |
| 1 | {使用者做的動作} | {系統應呈現的畫面/狀態} |
| 2 | ... | ... |
| N | {最後一步} | {代表流程成功完成的最終狀態} |
```

- 案例編號 `TC-01`、`TC-02`… 依情境數量遞增，不要跳號。
- 「操作」寫使用者實際會做的動作（點什麼按鈕、填什麼欄位），不要寫系統內部邏輯。
- 「預期結果」寫**畫面上看得到**的東西（文案、狀態、跳轉頁面），不要寫 DB 欄位
  異動——那是規格書的事，QA 案例是給人照著操作驗收用的。
- 多條 happy path 就依序 `TC-01`／`TC-02`…全部放同一個回覆／文件裡，前面加一句
  「共 N 條 happy path，未涵蓋邊界/例外情境」提醒範圍。

## 對應章節連結（附錨點）

使用者要求案例附上對應 HackMD 章節連結時，一律用**傳統錨點格式**
`https://hackmd.io/@<teamPath>/<shortId>#<anchor>`，不要用 `?stext=...` 那種
「精準文字選取連結」——後者是 HackMD UI 複製時才會產生時間戳＋隨機碼，且一旦
文件裡有 HTML 區塊（步驟圖常用的 `<div>`／HTML entity）就會跟原始 markdown 字元數
兌不上，從外部沒辦法可靠算出來（已實測驗證過會算錯）。

**錨點算法**（已用多組 HackMD 實際複製的連結逐一驗證）：

1. 標題開頭的章節編號**去掉點號**：`1.3.4` → `134`、`2.8.1` → `281`。無編號的標題
   跳過這步。
2. 空白字元換成 `-`：`篩選 Tab` → `篩選-Tab`、`新增封鎖 Lightbox` → `新增封鎖-Lightbox`。
3. **大小寫原樣保留，不要轉小寫**——`Tab`／`Lightbox` 開頭字母是大寫，錨點裡也是
   大寫（曾經猜成全小寫，錯）。
4. 中文字元組出錨點字串後，要對整段做 URL percent-encode（UTF-8）；純 ASCII
   （英文字母、數字、`-`）維持原樣不編碼。範例：`1.1 篩選 Tab` → 錨點字串
   `11-篩選-Tab` → 連結 `#11-%E7%AF%A9%E9%81%B8-Tab`。
5. **未驗證、遇到時要小心**：全角冒號 `：`、斜線 `/` 等符號在錨點裡怎麼處理還沒
   實測過。標題含這類符號時，優先改連結到底下不含符號的子標題（例如
   `1.3.8 面試/錄取通知摘要列` 底下的 `#### 面試摘要展開` 沒有斜線，改連過去），
   或請使用者直接在 HackMD 上對該標題按「複製連結」貼給你核對，不要憑這條規則
   硬猜再宣稱一定對。
6. 給使用者連結前，能驗證幾個就驗證幾個（找一兩個使用者已經貼過的真連結回頭核對
   算法），沒把握的要老實標「不確定」，不要整批都用同一套猜測值蓋過去。

## 輸出位置

預設直接在對話裡給 Markdown 表格。只有使用者明確要求「存進 HackMD」時才建立/更新
HackMD note，且要走 `wiki/hackmd_rules.md` 的安全回寫流程（先落地 baseline 再
PATCH），版控紀錄比照 `spec-doc-1111` 慣例新增一列。不要沒被要求就自動發佈。
