# 數據報告產生器（report-generator）

把分析結果寫成**人類一眼能懂**的報告。核心原則：**讀者只有 30 秒，先給答案；想深究的人自己往下讀。**
這條鐵律對 MD 與 HTML 兩種輸出格式**都成立**——差別只在 HTML 多了圖表與互動層，敘事骨架不變。

> 與 `tabular-token-min`（運算在腳本、只輸出最終表）、`md-datalayer`（讀 MD 不回讀 Excel）搭配使用：本 skill 管的是「算完之後怎麼寫／怎麼做成報告」。

## 先選格式：MD 還是 HTML？

| 情境 | 用 |
|---|---|
| 內部稽核、要貼進 HackMD／PR、讀者會用文字搜尋或複製數字 | **MD**（§A） |
| 要給人看圖表趨勢、要離線分享單一檔案、有多組圖表需要 hover 細節 | **HTML**（§B） |
| 不確定 | 先問使用者交付形式，不要預設 |

兩者共用的鐵則：**結論先行、指標白話命名、表格/圖表瘦身、案例節制、方法與限制永遠放最後**。

## §A：MD 報告

### 鐵則

#### 1. 結論先行（金字塔原則）
- 報告最上方必須有 **「TL;DR」區塊：3~5 行以內**，每行一句話 = 一個結論 + 一個關鍵數字。
- 順序：**結論 → 依據 → 明細 → 方法**。方法與限制永遠放最後一節。
- 讀者若只讀 TL;DR 就離開，也要能做出正確決策。

#### 2. 指標命名 = 白話 + 業務意義，定義只寫一次
- 指標名稱要**自帶意思**：用「前5名內猜對%」而不是 `top5_cum_pct`；用「完全猜錯%」而不是「無關%」。
- **以業務上真正有意義的口徑當主指標**（例：前端只顯示 5 筆 → 命中率就以前 5 名為準；其餘口徑標註「僅供驗證」），並在報告開頭一句話講明為什麼。
- 所有指標定義集中在**開頭一個「怎麼讀這份報告」小節**，正文和表格不再重複解釋。表格上方最多一行提示，不逐表重寫定義。
- 每個百分比都要能回答：「**分母是誰、分子是誰**」。範例句式：「每 100 筆 X，有 N 筆 Y」。

#### 3. 表格瘦身
- **一張表 ≤ 6 個數字欄**。欄位再多就拆表或砍欄——問自己：「這欄會改變讀者的下一步嗎？」不會就刪。
- **主文只放 Top/Bottom N（10~15 列）**，完整明細丟附錄檔或 JSON，正文給連結。禁止在正文貼 50+ 列全表。
- 數字**取到小數 1 位或整數**；千分位加逗號；比例欄靠右對齊。
- 每張表**依你要講的故事排序**（依效益、依嚴重度），不要依筆數或字母序。
- 想強調的欄位**粗體欄名**，一張表只強調一個重點欄。
- 表格下方接**最多 3 條「白話結論」**，每條 = 「誰最好/最差/最值得做 + 一個數字 + 一句為什麼」。

#### 4. 案例節制
- 每個問題樣態**最多 2 個案例**，選最有代表性的；同一樣態的重複變體（同店名不同符號）算 1 個。
- 案例固定格式：`職缺原文` → 現有=X，推薦=Y（判定）。一行講完，不展開成段落。
- 每個樣態結尾**一句話改善建議**，動詞開頭（「先剝除…」「加權…」），不寫成論文式討論。

#### 5. 結構模板（固定用這個骨架）

```markdown
# <報告標題：一句話講清楚比什麼跟什麼>

> 來源／基準／腳本 各一行（可重跑路徑）

## TL;DR（30 秒版）
- 結論1 + 數字
- 結論2 + 數字
- 最值得做的一件事 + 預期效益

## 怎麼讀這份報告（指標定義，只寫這一次）
| 指標 | 白話意思（分母/分子） |

## 一、整體結果
一張總表 + ≤3 條白話結論

## 二、分組拆解（大類/中類/…）
Top/Bottom N 表 + ≤3 條白話結論；全表放附錄連結

## 三、（若有）最值得做的改善機會
量化「做了能撿回多少」+ 排行榜 Top N

## 四、錯誤樣態與案例
每樣態：一段話 + ≤2 案例 + 一句建議

## 五、方法與限制（給要驗證的人）
條列：口徑、去重、已知資料瑕疵、檔案位置
```

#### 6. 產出紀律
- 運算一律在 Python 腳本內完成（見 `tabular-token-min`），報告只放**算好的最終數字**；腳本與中繼 JSON 路徑寫進報告開頭，確保可重跑、可稽核。
- 修訂既有報告時：**口徑一旦改變，必附「新舊口徑對照表」**（同指標兩欄並排 + 差幾個百分點），並在 TL;DR 註明本次口徑變更。
- 報告寫完後自我檢查三題：
  1. 只讀 TL;DR 能不能做決策？
  2. 有沒有任何名詞/百分比是「沒讀完全文就看不懂」的？
  3. 有沒有超過 15 列的表格留在正文？

### 反例對照（來自實戰 review）

| ❌ 不要 | ✅ 要 |
|---|---|
| 同一個定義在開頭、表格上方、方法節講 3 次 | 定義集中一節，其他地方只放一行提示 |
| 正文貼 58 列全表 | 正文 Top/Bottom 10~15 列，全表給附錄連結 |
| 欄名 `top10_cum_pct`（僅驗證） | 欄名「前10名內%」，僅驗證的欄乾脆移出主表 |
| 8 個案例輪流講同一個問題 | 2 個最典型案例 + 一句建議 |
| 61.81%、72.18% 兩位小數 | 61.8%、72.2%（差異夠大時甚至取整數） |
| 結論埋在第四節的粗體字裡 | 結論就在 TL;DR 第一行 |

## §B：靜態 HTML 報告

把數據轉成一份**可離線開啟、自包含（self-contained）**的視覺化報告。§A 的敘事鐵則（結論先行、
白話命名、案例節制、方法與限制放最後）全部照搬；本節只補**HTML 特有**的流程與踩坑經驗。
範例產出：`data/未讀履歷統計/提醒信成效分析報告.html`（與其 `analysis/` pipeline）。

**視覺規格先行**：動手寫 CSS 前，先照 `references/設計描述五層面.md` 把字體／級距／留白／
配色／動態五個層面各寫成一句可量化的規格（「好看」「有質感」這種主觀詞不是規格）——參照最多
選 3 個、分工不同（定調性／定版型／定互動），並標明借用哪一層；一次只調整一個變項。

**版面設計卡關時**，先看 `references/html-templates/README.md`——裡面有 77 個從
`nexu-io/html-anything`（Apache-2.0）匯入的版面參考，挑一個場景相近的（`data-report`／
`dashboard`／`finance-report`／`exec-briefing-memo` 等）看它的區塊配置與 grid/flex 排法，
把看到的轉成五層面的描述句再實作；版型庫不夠用時，五層面文件裡還列了 6 個公開設計資料庫
（Awwwards／SiteInspire／Mobbin 等）與各自適合查什麼。
**但一定要照下面第5點把外部 CDN 全部拔掉重寫，不能直接複製它的 `example.html`**。

### 標準流程

1. **原始資料留在磁碟，不進 context**：依 `wiki/master_prompt.md` 的「Excel/CSV 漸進式分析」
   規範，用 pandas 讀取、聚合，只把**聚合後的統計數字**（不是逐列 raw data）寫成一份中繼
   `summary.json` / `report_data.json`。所有中間運算（分組、比率、分佈）都在 Python 裡做完，
   與 §A 第 6 點「產出紀律」同一原則。
2. **先讀 `dataviz` skill 再寫任何圖表**：形式選擇（`choosing-a-form.md`）、色彩指定
   （`color-formula.md`）、色盲安全驗證（`node scripts/validate_palette.js "<hex,...>" --mode light/dark`
   ——兩個 mode 都要跑）、mark 規格與間距（`marks-and-anatomy.md`）、hover/tooltip
   （`interaction.md`）、上線前對照 `anti-patterns.md` 逐條檢查。不要跳過驗證腳本用肉眼判斷。
3. **模板 + 資料注入分離**：寫一份 `report_template.html`，內含 `__DATA__` 佔位符；一支
   build script 讀聚合 JSON、`json.dumps` 後字串替換注入，輸出最終 HTML。好處：改樣式不用重跑
   分析，改分析邏輯不用碰版面。
4. **深淺色雙模一定要用 Playwright 截圖驗證，不能只憑 CSS 邏輯推測**：
   ```js
   const p = await browser.newPage({ colorScheme: 'dark' }); // 'light' 另開一次
   await p.goto('file://' + path); await p.screenshot({ path: 'shot-dark.png', fullPage: true });
   ```
   本專案已有 Chromium：`executablePath: '/opt/pw-browsers/chromium'`（見系統環境設定，不要
   `playwright install`）。**必看兩張截圖**，逐張檢查有無：
   - 文字被圖形元素（誤差線、gridline）穿過或重疊（實際踩過的坑：長條圖上方數值標籤被
     min-max 誤差線的鬚穿過，改成貼齊誤差線頂端才修好）
   - label/tooltip 溢出容器、深色模式下對比度不足
   - `page.on('pageerror'/'console')` 監聽有沒有 JS 錯誤
5. **自包含（self-contained）鐵律**：CSP 情境下無法載外部 CDN/字型/圖片。CSS 用
   `<style>` 內嵌、圖表用純 SVG＋vanilla JS（不依賴 D3/Chart.js 等外部庫）、`prefers-color-scheme`
   做預設＋`:root[data-theme]` 做手動切換覆蓋（雙向都要贏）。
6. **Pipeline 要能重跑，不是一次性產物**：拆成 `stepN_xxx.py`（分析）與
   `stepM_build_report.py`（注入模板出圖），加一份 `README.md` 寫清楚輸入資料目錄結構、
   執行指令、已知資料落差／清洗規則。驗證方式：重跑一次比對輸出是否 byte-identical。
7. **交付**：檔案存進 repo 對應資料夾＋更新 `.claude_index.md`；同時用 `SendUserFile`
   （`display: render`）把 HTML 送給使用者當場預覽，不要只給檔案路徑。

### HTML 報告的內容準則（非圖表視覺，是敘事結構）

與 §A 完全一致，僅換句話：開頭一律先給 **TL;DR 結論句**（含關鍵數字），再展開方法論與圖表；
若分析基於代理指標（proxy，例如「消失＝已讀」這種無法直接觀測的推論），**必須有獨立一節
列出限制聲明**；結尾一定要有「建議的產品行動方案」，不能停在數字覆述。全文繁體中文（台灣）。
