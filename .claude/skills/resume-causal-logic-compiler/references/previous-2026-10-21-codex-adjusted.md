# Resume Causal Logic Compiler

> 來源：本人 2026-10-21 提供原始 skill（`references/original-user-version.md`）；Codex 調整版（`codex/resume-writer` a62650e）；Career Move 加〈驗收測試〉與固定入口。**這是寫作前的強制門檻**：`104resume`、`104coverletter`、`polish-104`、`resume-craft` 中文履歷流程都必須先過本檔 §對外選材，再修句。

## 邊界

- 事實只讀 career/library/ 及本人當次確認；先讀 decisions、superseded、相關 facts 與 about-me，再讀指定稿。
- 不另建有效 SSOT。實體表只作閱讀映射，逐項附來源與狀態；新事實交共同來源維護者記錄。
- 本人是規劃者、協作者、驗收者、時程掌控者。動詞依真實責任，不強制用架構、開發或規模化。
- 不以模型分數或 Level 選稿。文件中的目標、推測與示意文案不視為實測成果。
- 每輪只寫自身授權範圍；來源、工作稿與 PDF 各維持共同路由，不建第二份 current。

## 寫之前的對外選材檢查

- 若本人反映像工作報告、外部人看不懂或因果怪，切換到指定段落的內容重整，先寫讀者應記住的 1–3 個重點，不直接沿原句微調。
- 候選素材先分採用、合併、面試備用、不對外。每項說明其產品責任、判斷、產出、成果或必要背景；只有事實來源而沒有對外用途，不得直接放正文。
- 先問這項資訊是否能幫外部人理解產品責任、判斷或成果，及是否適合對外。
- 不公開尚未公布的功能順序、被延後項目、未來上線日期、內部代碼及細部遷移／開關規則。來源保留不等於對外必寫。
- 已發生的日期只在必要期間、歸因或成果脈絡中保留；未完成案例必須標真實狀態，但不預告內部 roadmap。
- 不將同一產品的不同專案自動串成因果，不套用固定「基建→功能→數據」順序。

## 核心規則

1. 禁止先使用後面才定義的特定產品、系統或業務概念；首次出現給最少足夠的類型、對象或問題。
2. 每點須能單獨辨認在什麼產品情境、本人做什麼、已知結果或狀態。不為通過測試重複整個公司背景。
3. 有可信成果可先寫，但同句須定義情境。沒有量化資料就寫已確認產出或狀態，不強迫補商業影響。
4. 保留本人形成方案與說明判斷的含義。規格、原型與驗收是可用的 PM 產出，不一律當日常瑣事剔除。
5. 區分團隊成果、本人責任、公司規模、資料觀察與因果。新資料與舊稿衝突時留問題，不自己猜。

## 四階段輸出（依序，與投遞正文隔離）

### Phase 1 實體與證據映射

列原詞、外部說法、職位／期間、來源及確認狀態、首次出現位置；需要移出對外稿的詞也標出。

### Phase 2 大綱與單向依賴

列每點引入概念及依賴；先定義必要背景，再寫行動。重新排序或補最短背景，不把所有前提搬進每一點。

### Phase 3 審查摘要

用精簡清單記首次定義、獨立可讀、因果／歸因、實際狀態、對外披露、責任及數字來源是否通過，並指出可核對的修正。只交付檢查結論與依據，不將內部推演貼入履歷。

跨欄位搜尋相同專案與概念，確認經歷修掉的內部資訊沒有留在專案、自傳或專長。以真實舊錯誤作驗收樣例：投票名次、預計日期、未先定義任務、SweetRing 職責遺漏、照片目標誤當成效、同一 roadmap 在別欄殘留。任一項失敗就回到選材，不直接渲染或標定稿。

### Phase 4 隔離正文

輸出乾淨的完整 Markdown 片段，無粗體分類前綴。每點以具體對象與動作成立；保留職位與產品情境所需的導航。修改理由、來源與未確認項另放非投遞區。

## 交付與同步

- 第一至三階段是編輯附件，第四階段才是可選用正文；不把完整表格給 HR，也不宣稱獨立驗證。
- 交付前比較原意：不為縮字丟掉必要限制、不為完整背景堆成工作報告。
- 新本人事實及偏好交維護者當輪同步 About Me／facts／decisions，標明是否已寫入；文案採用與事實確認分開。
- 本人未指定定版或重產時，保留草稿及 PDF 狀態；排版問題先處理版式，不以縮字級或刪敘事解決。

## 驗收測試（Career Move 每次交付前必跑；任一失敗＝不得標「可填表／定稿」）

| # | 測試 | 判定方式 |
| :-: | :-- | :-- |
| T1 | 未公開排序 | 全文（含專案、專長、自傳）無「第一名／票選第一／排名第二／業務投票」等具體排序或投票結果 |
| T2 | 未來日期與延後項 | 無「預計 YYYY/MM」「延後○○功能」「○○開發中」等 roadmap；進行中只寫「目前仍在進行中」 |
| T3 | 任務先定義 | 每個職位第一點先讓人知道產品情境與本人任務，再進細節（例：先寫「接手企業端招募系統改版」，不是先寫後台、信箱例外） |
| T4 | 職責完整 | 各職位職責涵蓋 library 已確認範圍（例：SweetRing 含產品維運與功能優化，不只在地化／支付） |
| T5 | 目標≠成效 | 文件中的目標、提示文案、預期值（例：照片提示「150%」）不得出現為已達成成果 |
| T6 | 跨欄位一致 | 經歷移除的內容，在專案、專長、自傳、求職信、簡介中也不得殘留（grep 同一關鍵字） |

執行：對交付檔逐條 grep／閱讀，把結果寫在交付檔末或 run 紀錄；失敗項回到 §對外選材。
