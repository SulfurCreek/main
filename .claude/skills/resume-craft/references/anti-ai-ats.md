# 去 AI 感＋ATS 規範（2026-10-08 使用者提供，整合版）

> 來源：使用者提供的 `anti-ai-ats-resume-crafter` skill 草稿。整合進既有規範，**與 `resume-voice-zh.md` §7（規劃者定位）衝突時以 §7 為準**。

## 1. 禁用詞與標點
- 英文：Delve、Tapestry、Navigated、Seamlessly、Testament to、Transformative；Spearheaded 全份最多 1 次。
- 中文：致力於、深入探討、扮演關鍵角色、成功實現了、無縫接軌、編織出；另沿用既有清單：賦能、驅動、顯著、指數級、戰略性、卓越、締造、擘劃。
- 不用破折號（—）串句，改逗號或拆句。
- 台灣用語：寫「API 串接、專案、提升營運效率、落地、重構」，不寫「應用程式接口、項目、優化了運作」。

## 2. CAR 盤問（不准只美化）
遇到空泛條目（例「負責系統改版」），**先停下來問使用者**：
- Context：在什麼背景下做的？
- Action：用了什麼方法、跨了哪些部門？
- Result：有什麼可驗證的數字？
問不到就照實寫過程，**不得補數字或情節**（2026-10-06 曾因自行補句被審查抓到）。

## 3. 對 JD 不鸚鵡學舌
- 不照抄 JD 原句；用使用者的真實經驗與工具改寫對應。
- 關鍵字自然分布，同義詞替換（Scrum／Sprint／站會），單一關鍵字不重複堆疊。

## 4. ATS 格式
- 單欄、純文字 Markdown；不放表格、圖表、技能星等。
- 標題只用通用名稱：工作經歷、學歷、專業技能（英文版 Experience／Education／Skills）。
- 日期一律 YYYY/MM。

## 5. 流程
1. 掃描並移除 AI 詞與視覺元素 → 2. CAR 檢查，空泛就停下來問 → 3. 改寫（結果在前、做法在後，但主詞維持規劃者）→ 4. 只輸出履歷本體，不加客套話。

## 與既有規範的整合說明
- **結果在前**：成果有數字時放前面；沒數字時不硬湊，維持「情境＋決定」。
- **104 匯入版不受「不放表格」影響**（104 本來就是欄位制）；此規則主要用於 PDF／英文 ATS 版。

> 注意：V4 原文引用的「§7 規劃者定位」在個人線分支，不在 main。main 上只保留 §1–§6；寫作時若與使用者的定位衝突，以使用者說明為準。

## 6. V4 防禦型去潤飾（2026-10-08 使用者再次提供，Toxic HR Defense）
以「挑剔、找理由刷人的審查者」角度先做毒性稽核，再改寫。
- **RACR，結果先行**：每條先寫可量化的結果，再寫行動與限制。**沒有真實數字的條目不硬套**，改寫限制或決定，不得編數字（§2 優先）。
- **職稱包裝**：資歷 7 年以上但在地職稱偏低（產品企劃、主任）→ 以實際範圍寫英文職稱，在地職稱放括號，例如「Product Owner（產品企劃主任）」。
- **量級錨定**：倍數一定要附規模，例如「男性 DAU 約 1,500 → 約 1.2 萬」，不只寫「8 倍」。
- **產業洗白**：「交友 App」→「高流量訂閱制 B2C App」，講商業模式不講內容類型。
- **剔除弱訊號**（⚠️ 使用者 2026-10-08 調整：AWS、交換、新蛋、遠端意願**保留**，放後段、不誇大層級）：5 年以上資歷刪除入門證照（AWS Cloud Practitioner）、10 年以上的交換與工讀經歷。
- **移除紅旗**：「遠端工作」等條件不寫在履歷，留給面談。
- **反日常勞力**：不把日常勞動寫成成就（「負責蒐集需求」「每天寫 user story」）。⚠️ 2026-10-08 使用者裁定：**PM 產出物與交付鏈必須呈現**（Journey、User Story、Use Case、SA、流程圖／循序圖、Wireframe、Prototype、Spec、QA 協作、上線計畫），把產出物當成「怎麼做到」的證據寫進成果條列，見 `career/library/decisions.md` §7。站會、Kanban 依使用者裁定保留。
- **動詞**：禁用 協助、參與、負責、處理、管理；改用 主導、上線、優化、定義、規模化。⚠️ 與事實衝突時以事實為準：只是協作的產品**直接刪除**，不能升級成「主導」。§7 規劃者定位仍適用，不用「架構」這類工程動詞。
- **結構去 AI 感**：條列開頭不加粗體摘要；條目長短不一；寫出限制與妥協（舊系統、分階段、時程壓力），不寫完美勝利。
- **輸出**：單欄純 Markdown／純文字，不加對話式說明。
