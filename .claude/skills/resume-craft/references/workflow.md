## 步驟 1：調用職能與職缺

- **JD 全文已由使用者提供**：先讀 `career/104/jd-digest-A.md`（A 級 15 筆摘要），需要其他筆或全文時查使用者上傳檔（51 筆 md）；**不要再向使用者索取 JD**。
- **必用職缺**：讀 `career/104/jobs-2026-10.md`（分級）與 `career/104/analysis.md`（46 份 JD 的需求頻率）或使用者貼的 JD；產出「JD 需求 → 履歷落點」對照，決定主版或某類職缺版（支付、B 端 SaaS、AI、電信）。
- **必用 career-ops**：目標職缺 URL 寫進 `career/career-ops/data/pipeline.md`；`CAREER_OPS_ROOT=/home/user/main/career/career-ops`，先跑 `npm run doctor`（在 `/home/user/career-ops`）。

- 讀：`career/library/`（decisions → profile → facts-1111／facts-prior）、`career/competency-framework.md`、F01–F15 分頁；目標 JD（若有）。
- 產出 `01-competencies.md`：
  - 本次要涵蓋的職能（F01–F15 逐項標「納入／刻意不放＋理由」）。
  - 交付鏈 14 項（`decisions.md` §7）逐項標落在哪個專案。
  - 目標讀者與市場版本（104／Cake／英文 ATS）、頁數上限。
  - **JD 關鍵字兩組**（步驟 4、7 評分用）：必備詞、加分詞（Preferred Qualifications；`career/style/ats-2026-source.md`：加分條件才是雇主真正的願望清單）。
- 出口條件：每個 F 職能與交付鏈每項都有去向，沒有「忘了」。

## 步驟 2：蒐集證據

- 產出 `02-evidence.md`，每個職能或專案一張表：`事實｜數字與口徑｜來源（library 條目或 wiki 檔）｜可寫程度（✅可寫／⚠️需確認／❌不可寫）`。
- 規則：
  - 事實只取 library；wiki 只補細節，衝突以 library 為準；逐條比對 `superseded.md`。
  - 規模脈絡 ≠ 個人貢獻；相關 ≠ 因果；保密範圍依 `decisions.md` §4。
  - 缺口一次問使用者一題（商業影響 → 規模 → 方法工具），**答覆當下先寫 library**，再繼續。問不到就標〔待補〕，不補數字。
- 出口條件：每條要進履歷的主張都有 ✅ 的來源。

## 步驟 3：每個項目寫成小 essay

- 產出 `03-essays.md`：每個專案或職能 150–400 字白話短文，欄位自然融入，不套條列：
  1. 當時的處境與限制（舊系統、時程、人）
  2. 我做的決定與為什麼（含取捨、不做什麼）
  3. 我實際做的事與產出文件（Journey、User Story、Use Case、SA、流程圖、Wireframe、Prototype、Spec、QA、上線計畫，依實際）
  4. 跟誰協作、怎麼說服或對齊
  5. 結果與數字（含口徑）；沒有就寫「結果數字待補」
  6. 我負責的與不負責的（角色邊界：規劃、協作、驗收、時程；不寫工程實作）
- **essay 就要對照職缺（使用者 2026-10-08 裁定）**：每篇開頭標「回應的 JD 需求」（取自步驟 1 對照表，例：跨部門 36／46、驗收 28／46），內文用 JD 的說法描述同一件事（例：JD 寫 UAT，就說明驗收怎麼做），不為了 JD 新增事實。
- **ATS 2026 洞見（`career/style/ats-2026-source.md`，2026-10-09）**：
  - 每篇都要拆得出 **X 結果＋Y 指標＋Z 做法**；缺 Y 標「指標待補」，不讓 essay 只剩過程。
  - 先對照 JD 的**加分條件**，再對照必備條件；用 JD 原詞描述同一件事。
  - 用到 AI 的專案，寫清楚 **AI 做了哪一段、省了什麼或多產出什麼**，不只寫「使用 AI 工具」；沒數字就不寫數字。
  - 第一句寫結果或處境的關鍵，方便步驟 4 產出「開頭就有結果」的版本。
  - 職稱落差、轉職動機等「2 秒內會被誤判」的資訊，在 essay 先寫清楚。
- **先寫完整，不管長短**——這一步不精簡。essay 是下一步的原料，也是自傳與面試備忘的來源。
- 出口條件：每個 essay 能讓不懂背景的人看懂「做了什麼、為什麼、結果如何」。

## 步驟 4：精簡×20 版本、取最高分、組裝（用 resume-craft）

- 依本 skill 的 Bullet 公式、市場版本範本、V4 防禦型規則（`anti-ai-ats.md` §6，與事實衝突以事實為準）。
- **範本與外部 skill 規則（使用者提供過，必須實際套用）**：繁中版用 `assets/template-tw-zh.md`（含 cv-resume-optimizer 採用項：**自傳每段 ≤ 4 行約 100–150 字、段間空行、不寫家庭背景、轉換動機一句正面交代、入職前 90 天須從 JD 推出、繁中 bullet 結果前置、缺資料一次問一題**）；作品集用 `assets/portfolio-case-study-tw.md`；去 AI 感用 `references/anti-ai-ats.md`。外部 skill 的採用／不採用清單見 `career/library/decisions.md` §9。

### 4a. 每個單位產生 20 個版本（2026-10-09 使用者裁定）
- **單位**：摘要、每條條列、技能欄、自傳每段。每個單位一次寫 **V01–V20**，等同一次產生 20 份履歷。
- 20 個版本只能改**寫法**，不能改事實；變化軸（每軸至少涵蓋幾個版本）：
  1. 結果前置 vs 做法前置
  2. 短（≤ 40 字）／中（40–70 字）／長（70–100 字）
  3. JD 原詞 vs 白話
  4. 指標放法（絕對數字、前後對比、百分比）
  5. 是否帶限制或取捨（舊系統、時程、妥協）
  6. 協作對象寫不寫、寫幾個
- 產出 `04-variants.md`：格式「### U01 單位名」下列「V01: …」到「V20: …」。

### 4b. 評分，每個單位只留最高分
- 機械分 0–40：`python3 .claude/skills/resume-craft/scripts/resume_score.py variants drafts/<版本>/04-variants.md --jd "<必備詞＋加分詞>"`（長度、數字、前 20 字有結果或關鍵詞、關鍵詞命中但不塞詞、禁用詞、破折號與粗體）。
- 人工分 0–60（模型依清單給分並寫一句理由）：
  - 事實一致（**閘門**：任何不在 essay／library 的內容 → 該版 0 分）
  - HR 清單 HR-A…H（15）、主管清單 HM-A…H（15）、去 AI 感（15）、XYZ 完整度（15）
- 總分最高者勝出；同分取較短者。勝出版本與次高版本都記在 `04-variants.md` 的評分表。

### 4c. 組裝成最完整的履歷
- 把每個單位的勝出版本組裝成 `04-resume-draft.md`，再做整份檢查（單看一條最好，放在一起不一定最好）：
  - 每段經歷 3–6 條、每條 1–2 行、一條一件事；不同條之間句型與開頭不重複（避免結構太整齊）。
  - **職能覆蓋檢查**：交付鏈定義段、交付段各至少一條；技能欄列出產出物；F 職能對照表無遺漏。
  - 少用工程實作詞與內部縮寫，**不得因此刪除 PM 產出物名稱**。
  - 作廢說法 0 命中（逐條比對 `superseded.md`）。
  - 整份不合格時，該單位改用次高版本，不重寫新事實。
- 附 **essay 去向表**（每段 essay → 履歷第幾條／自傳／面試備忘／捨棄＋理由）。
- 出口條件：每個單位都有勝出版本與分數；essay 去向表沒有未處理項目。

## 步驟 5：檢測讀者的 AI 感受、去 AI 化

- 產出 `05-de-ai.md`：把履歷當成讀者（人資、主管、AI 掃描器）看，逐句標 AI 感。檢查項：
  1. 禁用詞與破折號（`anti-ai-ats.md` §1）。
  2. **結構太整齊**：每條句型一致、長度一致、每段都三條並列、每條都「動詞＋名詞＋結果」。
  3. **空泛通用句**：換成別人也成立的句子（例：「重視使用者、讓第一線聲音進決策」）→ 換成本人獨有的情境或刪除。
  4. **無來源的形容與感受**：沒有 library 事實支撐的描述（例：「抱怨明顯少了」）。
  5. **過度完美**：全是勝利、沒有限制與妥協；補上真實限制。
  6. **念出來測試**：不像人會講的句子重寫；與 `style/resume-voice-zh.md` 的語氣比對。
  7. **essay 與履歷的聲音落差**：履歷是否還保有 essay 裡的具體細節（人、地、數字、取捨）。
- 另檢查**自傳版面**：每段 ≤ 150 字、≤ 4 行、段間空行、無家庭背景、有轉換動機與 90 天（有目標 JD 時）。
- 輸出：每個被標句子 → 原句、問題、改寫；改寫不得新增事實。
- 出口條件：自評「像本人寫的」；使用者之前點名過的 AI 腔（流水帳、套話）0 項。

## 步驟 7：ATS 檢測（2026-10-09 新增）

- 算分方針：`career/style/ats-2026-source.md`〈ATS 算分表〉（滿分 100）。核心觀念：ATS 是讓招募者**搜得到**的資料庫，不是自動淘汰機器；驗證目標是「搜得到、解析得對、2 秒看得懂」，不是塞關鍵字。
- 工具：
  - A 格式（25）：career-ops `node verify-ats.mjs <cv.html> --keywords "<必備＋加分詞>"` 結構分數 ×0.25；有 critical 時 A ≤ 15。PDF < 2.5MB。
  - B 關鍵字對應（25）、C 7 秒可讀（20）、D 量化（20）：`python3 .claude/skills/resume-craft/scripts/resume_score.py ats <resume.txt> --jd "<必備詞>" --preferred "<加分詞>"`。覆蓋率 70–90% 滿分，≥ 95% 視為塞詞扣分；加分詞要同時出現在技能欄與經歷。
  - E AI 實證（10）：人工；寫出 AI 怎麼用、產出什麼，有作品集或連結佐證。
  - 一票否決：白字或隱藏文字、與經歷無關的關鍵字清單、無來源的數字（`verify-cv-facts`）。
- 產出 `07-ats-review.md`：五面向分數、缺的詞、只出現一處的加分詞、開頭沒有結果的條列清單。

## 回退規則（步驟 6、7、8 發現問題時）

| 問題類型 | 回到哪一步 |
| :--- | :--- |
| 事實缺口（無結果、無取捨、無在地化發現） | 步驟 2：問使用者，答案先寫 library，再補 essay |
| 太長、太細、條數過多；ATS 的 C 分（開頭沒結果）偏低 | 步驟 4（改選次高版本或重跑該單位 20 版） |
| ATS 的 B 分偏低（缺詞、加分詞只出現一處） | 步驟 3 確認事實上有做 → 步驟 4 重跑相關單位；沒做過的詞不補 |
| AI 感、套話 | 步驟 5 |
| 職能或交付鏈缺席 | 步驟 1（職能清單漏列）→ 2 → 3 → 4 |
| 只剩分數差距、無事實可補 | 不改；記在審查報告「需使用者提供」 |

- **不可只為了分數改稿**：任何改動必須能對回 library 事實或使用者裁定。審查分數上升若來自「補了清單要求的內容」，報告要明寫。
- 回退最多兩輪；兩輪後仍有缺口，列給使用者決定，不無限優化。

## 步驟 9：定版

- **career-ops 驗證（必做）**：把定稿轉成 HTML 後，在 `/home/user/career-ops` 跑
  `node verify-cv-facts.mjs <cv.html> --source $CAREER_OPS_ROOT/article-digest.md --source $CAREER_OPS_ROOT/cv.md`（每個數字都要在來源找得到）與
  `node verify-ats.mjs <cv.html> --keywords "<步驟 1 的 JD 關鍵字>"`（結構分數 ≥ 70、關鍵字覆蓋列入報告）。`article-digest.md` 由 `career/library/` 萃取，library 改了要同步。

閘門（全部成立才能定版）：

- [ ] 職能覆蓋核對 ✅（交付鏈兩段、F 職能對照表無未交代項目）
- [ ] 作廢說法 0 命中
- [ ] 事實核對無 ❌；⚠️ 項目已附面試說明或使用者確認
- [ ] 步驟 5 去 AI 感完成
- [ ] HR 與主管檢測無「必要條件缺席」類 ❌
- [ ] ATS 檢測 ≥ 75 分且無一票否決（104 表單版若本文無 Email，A 面向註明「表單另有欄位」）
- [ ] **使用者核可措辭**（未核可前不產 txt／PDF 給外部使用）

定版動作：

1. 產 `104/resume-104-v<版本>.txt` 與 PDF（104 規格見 `career/104/fields-spec.md`）。
2. 舊版移 `104/archive/`，更新 `104/README.md`、`HANDOFF.md`、`CLAUDE.md` 的現行版指標。
3. 新事實、新裁定寫 `library/`；被推翻的舊說法移 `superseded.md`。
4. `drafts/<版本>/09-final.md` 記閘門核對與核可日期。
5. 審查報告放 `104/review-<日期>-v<版本>.md`，並註明審查者是同一模型扮演、非真人意見。

## 常見偏差（已發生過，檢查用）

| 偏差 | 例 | 防法 |
| :--- | :--- | :--- |
| 把「少用技術詞」擴大成不寫產出文件 | v4～v5.2 | 步驟 1 交付鏈清單、步驟 4 覆蓋檢查 |
| 只從上一版刪修 | v4 之後 | 步驟 1–3 一律從 library 出發 |
| 為分數優化 | 精簡到看不出判斷 | 回退規則「不可只為了分數改稿」 |
| 自己編的感受句 | 「抱怨明顯少了」 | 步驟 5 項 4 |
| 把舊說法寫回 | JD2、零停機、主導 Peach | 步驟 4、9 作廢比對 |
| 塞關鍵字 | 為覆蓋率把 JD 詞堆進技能欄 | 步驟 7：覆蓋 ≥ 95% 扣分；沒做過的詞不寫 |
| 只產一版就定稿 | v1～v7.1 | 步驟 4 每單位 20 版本取最高分 |
| library 只收更正、漏收既有能力 | 2026-10-08 稽核 | 步驟 1 對照 competency-framework 與 F01–F15 |
